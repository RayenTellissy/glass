# Decision Log

Every decision that shapes Glass is recorded here, oldest first. Each entry expands one line of the Decision Log at the bottom of `PLAN.md`.

How to add a decision:

- Append one line to the Decision Log in `PLAN.md`: `- YYYY-MM-DD — <decision>. Reason: <reason>.`
- Append the same decision here as a new entry, with more context where it helps: what it changes, what else was considered, and where the evidence lives.
- Changing a Phase 0 default, dropping a task (`[-]`), or raising a budget always needs an entry in both places. A Phase 0 default changes only when a benchmark in this repo proves it fails a budget.

Entries are never edited after the fact except to fix typos. A decision that reverses an earlier one is a new entry that names the one it replaces.

## 1. Adopt the Phase 0 defaults table as the starting stack

- **Date:** 2026-09-29
- **Decision:** Use the defaults table in PLAN.md Phase 0 as the starting stack: `egui`/`eframe` on `winit` for UI, `wgpu` with WGSL for the GPU, `ffmpeg-next` for decode and encode, VideoToolbox, D3D11VA then NVDEC, and VAAPI for hardware decode with a software fallback, `cpal` for audio, `cosmic-text` for text, `im` and `serde_json` for project data, `wasmtime` with the Component Model for plugins, `whisper-rs` for speech-to-text, `cargo-dist` for packaging, and macOS 12 plus Windows 10 as minimum targets.
- **Reason:** Fastest path to a single small binary on both platforms.
- **Alternatives:** Each row names a fallback in PLAN.md: `iced` for UI, `rustybuzz` + `swash` for text shaping, `rpds` for persistent data, hand-written CI for packaging, software decode for hardware decode.
- **Consequences:** A default changes only when a benchmark in this repo proves it fails a budget. The prototypes confirmed the UI toolkit, `wgpu` on Metal, `cosmic-text` and VideoToolbox decode on Apple silicon; see `docs/ARCHITECTURE.md` section 11 for the status of every row.

## 2. Free and open source under MIT; licensing and activation dropped

- **Date:** 2026-09-29
- **Decision:** Glass is free and open source, with source code under MIT. The Phase 17 task "Licensing and activation" is dropped (`[-]`).
- **Reason:** Product decision.
- **Consequences:** No activation, no paid tiers, no telemetry. This later made the GPL FFmpeg build possible (entry 5).

## 3. Priority is speed, then features, then size

- **Date:** 2026-09-29
- **Decision:** When goals conflict, speed wins over features, and features win over size. The 30 MB installer size target gives way to features and speed optimisations, and release builds ship with every feature flag on.
- **Reason:** Product decision.
- **Consequences:** The speed budgets (UI frame under 8 ms, scrub under 50 ms, project open under 1 s, cold start under 1.5 s) are hard. The size budget can be raised, but each raise needs a Decision Log entry. Asset packs and models still download on demand.

## 4. Creators come first; pro tools are how the app grows with them

- **Date:** 2026-09-29
- **Decision:** Creators making videos for YouTube and social platforms are the primary audience. When their needs conflict with a pro's (defaults, what the app opens to, what shows without digging), the creator wins. Pro tools (colour, audio, compositing, multicam) never make the beginner path harder.
- **Reason:** Product decision.
- **Consequences:** The design splits into beginner surfaces (first run, storyboard, guided flow, browsers) and dense pro surfaces (timeline, colour, audio, inspector), as set out in `DESIGN_HANDOFF.md`.

## 5. GPL FFmpeg build with x264 and x265; release builds under GPLv3

- **Date:** 2026-09-29
- **Decision:** FFmpeg switched from an LGPL build to a GPL build with x264 and x265. Release builds are distributed under GPLv3; the source stays MIT.
- **Reason:** Better software H.264 and HEVC encoding, and the LGPL limit only mattered while a commercial licence was possible.
- **Alternatives:** An LGPL FFmpeg build without x264 and x265, which kept a commercial licence open. Entry 2 removed that need.
- **Consequences:** Every release bundles the licence texts and attaches the exact FFmpeg, x264 and x265 source archives used. `cargo-deny` allows only GPLv3-compatible licences. The About dialog shows both the MIT and GPLv3 notices.

## 7. proto-decode CPU budget judged as whole-machine utilisation

- **Date:** 2026-09-29
- **Decision:** The proto-decode budget "under 5% CPU per stream" is judged as whole-machine utilisation: the app process plus the system decoder service (VTDecoderXPCService on macOS), divided by the number of logical cores, at 60 fps paced.
- **Reason:** The plan does not define the unit; this is how system-wide decode cost is usually stated. The per-core numbers are recorded in `experiments/proto-decode/RESULTS.md` so the result can be re-judged on the reference M1.
- **Evidence:** On the M2 (8 logical cores), the judged run (CVMetalTextureCache per frame, paced 60 fps, one stream) used 2.18% of the machine: 9.20% of one core in the process plus 8.26% of one core in VTDecoderXPCService, at 60.1 fps with 0 late frames. Rerun after review with a true 3-frame pacing window (the first run allowed 6 slots) against the pinned FFmpeg 9.0.2: 2.06% of the machine (8.58% + 7.88% of one core), 60 fps, 0 late; two paced streams 1.81% each, 0 late. The verdict is unchanged.
- **Alternatives:** Judging against a single core. Measured that way, the same run is above 5% (9.20% in the process alone), so the unit decides the verdict; the per-core figures are kept for that reason.
- **Consequences:** Later "under X% CPU" budgets are judged the same way, with per-core numbers recorded alongside.

## 11. egui without its default fonts

- **Date:** 2026-09-29
- **Decision:** `egui` is used with its `default_fonts` feature off (workspace dependency `egui = { version = "0.36", default-features = false }`; `eframe` likewise). Glass ships its own fonts, Geist and Geist Mono (OFL), from `assets/fonts/` and installs them into the egui context.
- **Reason:** `default_fonts` bundles the Ubuntu font, whose licence has no FSF compatibility ruling, so `deny.toml` does not allow it. The design uses Geist and Geist Mono anyway (section 8 of `docs/ARCHITECTURE.md`).
- **Evidence:** Without any font, egui 0.36 lays out text with zero width and draws nothing, so the fonts are required, not optional. `cargo tree -e features -i epaint` shows no `default_fonts` feature enabled.
- **Consequences:** Until the Geist files are added to `assets/fonts/` (400, 500, 600 and Mono 400, 500, from the official vercel/geist-font release, with the OFL text), the headless test harness in `ui::headless` loads a system font at test time (never bundled) and draws shapes only when none exists.

## 13. dav1d in the pinned FFmpeg build for AV1 software decode

- **Date:** 2026-09-29
- **Decision:** The pinned FFmpeg build adds dav1d for AV1 software decode, with meson and ninja built from pinned sources as host tools.
- **Reason:** AV1 is a supported format (the `codec-av1` flag, the fixtures, export) and FFmpeg's built-in AV1 decoder only drives hardware decoders, which the M1/M2 lack (AV1 hardware decode arrived with the M3).
- **Details:** `scripts/ffmpeg/versions.env` pins dav1d 1.5.4 (BSD 2-clause), meson 1.12.1 and ninja 1.13.2 by URL and SHA-256. `build.sh` bootstraps ninja with its `configure.py`, runs meson from its unpacked source with `python3`, builds dav1d as a shared library into the same prefix, and configures FFmpeg with `--enable-libdav1d`. meson and ninja are build tools only and are not shipped; dav1d's `COPYING` joins `LICENSES/` and its archive joins the release source bundle.
- **Consequences:** The local prefix grows from 32 MB to 32.8 MB (libdav1d is 0.9 MB). `cargo deny` is unaffected (a C library). python3 must be on `PATH` where the FFmpeg build runs; the CI runners have it.

## 14. Content hash without the modification time

- **Date:** 2026-09-29
- **Decision:** The content hash that keys the project cache folder's per-file analysis is BLAKE3 over a version tag, the file size, the first and last 1 MiB and eight evenly spaced 64 KiB blocks. It does not include the modification time.
- **Reason:** The cache must survive relinking, renaming, moving and copying media (ARCHITECTURE section 6), and a copy gets a new modification time. Sampling keeps hashing at 2.5 MiB per file whatever its size.
- **Details:** `media::cache::ContentHash::of_file`; files up to 2 MiB plus one block are hashed whole. The accepted risk is two same-size files that agree in every sampled block; compressed media differs throughout after any change, and headers and MP4 indexes are always sampled. A version tag in the hash lets the sampling change later without stale matches.
- **Consequences:** Editing a file in place without changing its size or any sampled block would reuse stale analysis; tools that do that (metadata editors that rewrite a fixed-size field in the middle of a file) are rare for video. A user-facing "rebuild analysis" action covers it.


## 15. Working primaries follow the project colour space

- **Date:** 2026-09-29
- **Decision:** The render working space is linear light in the project primaries: BT.709 by default, BT.2020 when the project colour space is HDR (PQ or HLG). Sources are gamut-converted into it by a render-graph node (Phase 4).
- **Reason:** Most creator footage and delivery targets are BT.709, and BT.2020 keeps HDR sources unclipped; the project colour space setting (Phase 5) already chooses between them.
- **Consequences:** `media::ColourSpace` carries source primaries; Phase 4 adds the gamut conversion node; Phase 11 colour management may add ACES on top.


## 16. Parallel tasks in separate worktrees

- **Date:** 2026-09-29
- **Decision:** Independent tasks now run in parallel in separate git worktrees, including tasks from the next phases whose inputs are already built. Cargo commands are serialised by `scripts/cargo-serial` and every worktree shares the main checkout's target directory. The hard limits stay: at most 10 agents, one cargo command at a time, 4 compiler jobs, serial benchmarks.
- **Reason:** The user asked for faster progress, and most agent time is spent outside the compiler (reading, writing, reviewing), so only the compiler needs to wait its turn.
- **Details:** `scripts/cargo-serial` holds an exclusive `flock` on `<git common dir>/glass-cargo.lock` for the whole cargo command, test runs included. `scripts/dev-env.sh` points `CARGO_TARGET_DIR` at `<main checkout>/target` and `FFMPEG_DIR` at `<main checkout>/.glass-cache/ffmpeg/<host>`, so crates.io dependencies and `ffmpeg-sys` build once for all worktrees. (Corrected by Decision 28: workspace crates do not get separate artifacts per worktree, because cargo hashes their path relative to the workspace root.) `scripts/worktree-setup.sh` prepares a new worktree. `PLAN.md` and `docs/DECISIONS.md` use git's union merge driver (`.gitattributes`) so branches that each append log lines merge without conflicts.
- **Consequences:** Replaces the earlier rule that only `(parallel)` tasks run beside the current phase task. With union merges, a line changed differently on two branches (the same checkbox marked `[~]` on one and `[x]` on the other) ends up in the file twice, so check `PLAN.md` after each merge. Killing `cargo-serial` with `SIGKILL` releases the lock while its cargo child may still run; stop it with Ctrl-C or `SIGTERM` instead.


## 17. `imbl` instead of `im` for the edit tree

- **Date:** 2026-09-29
- **Decision:** The project edit tree uses `imbl` 7 instead of `im` 15, the Phase 0 default.
- **Reason:** `cargo deny check` rejects `im`: it is unmaintained (RUSTSEC-2026-0248) and has an unsoundness advisory in `OrdSet` insertion with no fixed release (RUSTSEC-2023-0126). `imbl` is the maintained fork, with the same persistent `Vector` and `OrdMap`, the same structural sharing and the same licence (MPL-2.0, allowed by `deny.toml`).
- **Consequences:** Only `project` depends on it. The architecture doc's defaults table records the change.


## 18. Scoped checks on task branches, full test on the integration branch

- **Date:** 2026-09-30
- **Decision:** A task branch's finish check runs `cargo build --workspace`, `cargo test` for the crates it changed and every workspace crate that depends on them, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check` and the smoke binary, holding the cargo lock once for the whole sequence. The full `cargo test --workspace` runs on the integration branch after each batch of merges; a failure there is fixed before the next batch merges.
- **Reason:** One full check takes about 30 minutes of cargo time on the M2 (the workspace test alone about 22 minutes) and about 65 minutes end to end with other agents queued, so running it on every task branch kept most agents waiting on the lock.
- **Consequences:** A breakage that only shows in an unrelated crate's tests is caught one batch later, on the integration branch, instead of on the task branch. A phase still merges to `main` only after a full check passes on its branch.


## 19. Shader hot reload dependencies are not profile-gated

- **Date:** 2026-09-30
- **Decision:** `render` depends on `notify` 8 (default features off, macOS FSEvents backend) and directly on `naga` 30 (the version wgpu 30 uses, `wgsl-in`) in every profile; the watcher (`shader-watch` thread, `ShaderLibrary::watching`) is compiled only under `debug_assertions`, and release builds use the embedded shaders.
- **Reason:** Cargo cannot choose dependencies by build profile: it does not support `debug_assertions` in `[target.'cfg(...)'.dependencies]` tables. naga is already compiled for wgpu, so a direct dependency costs nothing, and naga validation stays usable in tests of every profile.
- **Consequences:** Release binaries contain no watcher code. notify brings a second `windows-sys` version, which `cargo deny check` reports as a duplicate warning; `cargo deny check` passes.

## 20. Blend modes on linear light, HDR-safe

- **Date:** 2026-09-30
- **Decision:** Layer blend modes are evaluated on premultiplied linear light in the working space (W3C Compositing and Blending Level 1, source-over with a separable blend function B, plus Add and Subtract). Where a W3C formula would clip or dim an HDR backdrop above 1, Glass keeps it: Screen takes max(Cb, Cs) once either is above 1, Colour dodge caps at max(1, Cb) instead of 1, Colour burn returns Cb for Cb >= 1.
- **Reason:** The working space is linear light (Decision 15) and holds values above 1; a neutral screen, dodge or burn layer should leave highlights alone. For 0..1 values every mode equals the W3C function.
- **Details:** `render::blend` (CPU reference, f64) and `crates/render/shaders/composite.wgsl`; `crates/render/tests/composite.rs` compares them for every mode.
- **Consequences:** Overlay and Soft light look somewhat different from editors that blend encoded sRGB values. Soft light and the other modes extrapolate their 0..1 formulas above 1.


## 21. Output encoding: inverse BT.1886 for SDR video, straight alpha, triangular dither

- **Date:** 2026-09-30
- **Decision:** `render::nodes::OutputNode` encodes SDR video tagged BT.709 with the inverse of the BT.1886 EOTF (a 1/2.4 power), not the BT.709 camera OETF; the preview and stills use sRGB; PQ is absolute (1.0 = 203 nits) and HLG goes through the inverse BT.2100 OOTF for a 1000-nit display. Outputs carry straight alpha unless a caller asks for premultiplied. 8, 10 and 16-bit integer targets get triangular-PDF dither of one code value from a PCG3D hash of pixel position and a per-frame seed; exact black and white are not dithered.
- **Reason:** players decode BT.709-tagged video with BT.1886, so the inverse EOTF makes display light round-trip with the working space, which is display-referred (the same convention `render::yuv` decodes with); the BT.709 OETF stays available (`OutputTransfer::Bt709`) for scene-referred delivery. Straight alpha is the delivery convention of ProRes 4444, PNG and most encoders. TPDF dither makes the quantisation error independent of the signal, removing banding without bias; varying the seed per frame keeps the pattern from sitting still.
- **Consequences:** Round trips through `media::TransferFn` are exact for sRGB, BT.1886, PQ and HLG. The dithered 8-bit output has no run of equal codes longer than a few pixels on a gradient that bands in 320-pixel steps undithered (`crates/render/tests/output.rs`).

## 22. Autosave in the per-user cache folder until projects have their own

- **Date:** 2026-09-30
- **Decision:** Autosaves go to `<cache>/autosave/<project uid>/`, where `<cache>` is the per-user cache folder (`~/Library/Caches/Glass` on macOS, `%LOCALAPPDATA%\Glass` on Windows, `$XDG_CACHE_HOME/Glass` on Linux, `GLASS_CACHE_DIR` to override) until the Phase 5 project settings task adds the per-project cache folder. The autosave format has its own version (`project::autosave::FORMAT_VERSION`, in every snapshot, log header and marker), separate from the project schema version, and autosaves of another format version are not read or migrated. The recovery prompt shows ages (`12 min ago`) instead of clock times.
- **Reason:** Project files and settings do not exist yet, so there is no project cache folder to write into, and the launch scan needs one known place to look. Autosaves are short-lived (deleted on a clean quit, on Discard, or seven days after the session was last alive), so migrating them is not worth the code; the saved project file is what schema migrations cover. Local clock times need a time zone library, which no task has chosen yet.
- **Consequences:** When project settings land, the app passes the project's cache folder to `engine::autosave` and the launch scan also looks in the recent projects' cache folders. The prompt's `autosave_time` and `saved_time` become local clock times once a date and time crate is added.

## 23. Layer transforms are sampled inside the composite pass

- **Date:** 2026-09-30
- **Decision:** A layer's transform (position, non-uniform scale, rotation, anchor) is applied inside `CompositeNode`'s pass: the shader maps each canvas pixel centre through the inverse matrix into the layer and resamples there (nearest, bilinear, or Catmull-Rom bicubic by default). There is no standalone transform node; opacity and crop are applied in the same pass. A transform that lands every pixel centre on a texel centre samples nearest whatever the setting. The shader has an entry point per filter and each pass uses the one for its most expensive layer filter; a per-pass cap (`CompositeNode::with_max_resample`) lets playback sample transformed layers bilinear, and paused frames and export use bicubic. The per-layer transform is a list of shutter samples (up to 16), of which the compositor renders the middle one until motion blur (Phase 13) averages them.
- **Reason:** Five 4K layers already take about 5.5 ms of the 8 ms Phase 4 budget, bound by memory bandwidth; a separate transform pass would add a full-frame `Rgba16Float` write and read per layer. Sampling in place costs only the extra texture fetches, which mostly hit the cache. Measured on the M2 (standing in for the M1): exact Catmull-Rom from nine bilinear fetches takes about twice the GPU time of bilinear for five full-frame 4K layers (texture-rate bound), a five-fetch approximation still about 1.6 times, and merely compiling the bicubic path into a pass slowed untransformed layers by about half, hence the per-filter entry points and the playback cap.
- **Details:** `render::transform` (matrix maths, `ShutterTransforms`, `Resample`, the CPU resampling reference), `nodes::Layer::reference`, `crates/render/shaders/composite.wgsl`; `crates/render/tests/transform.rs`.
- **Consequences:** A layer whose effects need its transformed pixels as a texture (a blur after scaling, for example) will need a transform node then; the maths is in `render::transform` for it. Strong downscaling samples without mipmaps and can alias.

## 24. Crop in layer pixels with an inward feather

- **Date:** 2026-09-30
- **Decision:** A layer's crop is four per-edge amounts in layer pixels, applied before the transform, plus a feather width in layer pixels. The feather ramps each edge of the crop rectangle inward with a smoothstep (0 half a pixel outside the edge, 0.5 at half the feather, 1 past it); with no crop it softens the layer's own edges. A hard edge is box-filtered over the canvas pixel's footprint. Opacity scales the layer's premultiplied colour before the blend.
- **Reason:** Cropping before the transform keeps the cut attached to the picture when it moves, turns or scales, as editors do. An inward feather never shows pixels the crop removed, and the smoothstep avoids the visible kink of a linear ramp's ends. Scaling premultiplied colour is how W3C compositing defines opacity and fades every blend mode towards the backdrop.
- **Details:** `render::crop` (CPU reference), `nodes::Layer::{opacity, crop}`, `crates/render/shaders/composite.wgsl`; `crates/render/tests/crop_opacity.rs`.
- **Consequences:** A proxy at a lower resolution than the source needs its crop, feather and transform scaled into proxy pixels by the caller (the same mapping as the transform's anchor).

## 25. Text: coverage atlas, vector outline strokes, graph shadow

- **Date:** 2026-09-30
- **Decision:** `render::text` rasterises glyphs to 8-bit coverage in one `R8Unorm` atlas (shelf packed, doubling up to 4096, then evicting glyphs unused this frame and repacking on the GPU). Outlines are round-join strokes rasterised by swash at twice the outline width, cached per glyph and width in the same atlas, instead of a signed distance field. The drop shadow is a separable Gaussian of the fill-and-outline union, as render-graph passes. cosmic-text 0.19 is built without its `fontconfig` feature.
- **Reason:** Coverage matches the CPU rasteriser exactly (GPU vs CPU max difference 0.0005), strokes stay crisp at any width without an SDF's range limit, and fontdb scans the standard font folders without fontconfig.
- **Consequences:** Each outline width is a separate atlas entry, so animating the outline width re-rasterises per step (quantised to 1/16 px). Per-glyph scale above 1 samples the atlas bilinearly; the text animator should lay out at the final size for large zooms. Colour glyphs (emoji) keep only their alpha and take the fill colour.

## 26. Media pool items are keyed by `MediaId`; colour labels use the clip palette

- **Date:** 2026-09-30
- **Decision:** A media pool item maps one to one onto a source media reference, so the pool keys items by `project::MediaId` (the draft's own `ItemId` is gone) and bins by a new `project::BinId` node id. Until the project root embeds the pool (Phase 5 schema work) the pool hands out ids from its own counter, and `MediaPool::insert_item` accepts ids chosen by the caller. The five colour labels are drawn in the clip roles: amber `clip/title`, blue `clip/video`, green `clip/audio`, red `clip/offline`, violet `clip/adjustment`, and always shown with their names.
- **Reason:** `project` already exports an `ItemId` for timeline items, and a clip's media reference and its pool entry are the same thing, so one id avoids a mapping table. The colour label menu on the `Sheet / Media pool` board uses exactly these clip colours, and the theme has no separate label roles.
- **Consequences:** Embedding the pool into `Project.media` later only swaps the id source. The search index is a derived cache and is never saved.

## 27. Frame queues: rtrb for one producer, crossbeam's ArrayQueue for the decode pool

- **Date:** 2026-09-30
- **Decision:** `engine::frame_queue` uses `rtrb` 0.4 for single-producer queues (render → present, one decoder → render) and `crossbeam-queue`'s bounded `ArrayQueue` for the multi-producer decode → render queue, with `crossbeam-utils`' `Parker` for waiting. Stale frames are flushed through a shared generation counter carried in every frame's stamp rather than by draining the queue under a lock.
- **Reason:** Both are lock-free, bounded and allocation-free per operation, and both pass `cargo deny check` (MIT or Apache-2.0, no new transitive crates; `crossbeam-utils` was already in the tree). `rtrb` is the fastest SPSC ring and can peek, which the present policy needs; it cannot take several producers, so the decode pool uses `ArrayQueue`. `std::sync::mpsc::sync_channel` (crossbeam's channel in std) was not used because a sender blocked on a full channel cannot be woken by a seek, and blocking decoders must return at once when the generation moves on.
- **Consequences:** Order is kept per producer only on the decode queue; render matches frames to requests by stamp. Push and pop fence once (`SeqCst`) to pair with the waiting flags.

## 28. `cargo-serial` forgets workspace fingerprints when the checkout changes

- **Date:** 2026-09-30
- **Decision:** `scripts/cargo-serial` records the top-level path of the checkout that last ran a cargo command in `<git common dir>/glass-cargo-last-checkout`. When a command comes from a different checkout (or the record is missing), after taking the lock and before running cargo it deletes the fingerprint directories of every workspace package (`cargo metadata --no-deps`) under every profile in the target directory (`CARGO_TARGET_DIR`, else `<main checkout>/target`), prints one line, and records the new path. Dependencies' fingerprints stay.
- **Reason:** Every worktree shares the main checkout's target directory (Decision 16), and cargo hashes a workspace member's path relative to the workspace root, so the same crate in two worktrees gets the same `.fingerprint/<pkg>-<hash>` directory and the same `deps/lib<pkg>-<hash>.rlib`. After worktree B builds a crate, worktree A's next build compares A's older source mtimes with B's newer outputs and treats them as fresh, so A compiles and tests against B's code: false "unresolved import" errors, or tests silently running another branch's build. Decision 16 wrongly said workspace crates get separate artifacts per worktree.
- **Consequences:** The first command after switching checkouts recompiles the workspace crates it needs (dependencies and `ffmpeg-sys` are not rebuilt). Only commands run through `cargo-serial` are protected: a plain `cargo` build in a worktree, or a worktree whose branch still has the old script, neither records its checkout nor clears the fingerprints, so every worktree should merge the phase branch to pick up the new script.

## 29. Offline media is runtime state, shown as a cached slate

- **Date:** 2026-09-30
- **Decision:** Whether a source file is available is checked by the engine (`engine::media_mgmt::offline`: missing, unreadable, or content hash changed) and kept in a map beside the project, never in the document. An offline clip renders `render::slate`: the viewer's offline state from the error and warning states sheet, drawn at the clip's size with sizes scaled from the 640 x 360 design frame, colours from the dark theme's roles (whatever the UI theme, since the slate is picture content that exports carry), without the design's Relink button (the preview draws controls over the picture). Each slate is rendered once per size and label and cached; frames import the cached texture.
- **Reason:** Keeping availability out of the tree means loading, editing, undo and saving never depend on the disk, and a relink or a remounted drive changes nothing in the document. One cached texture per size and label costs one layout and a few passes per offline file, then only an import per frame.
- **Details:** `engine::media_mgmt::offline`, `render::slate` (CPU reference `slate::reference`), `crates/render/shaders/slate.wgsl`; `crates/engine/tests/offline_media.rs`, `crates/render/tests/slate.rs`.
- **Consequences:** The design's glow blur (18 px) and backdrop blur are approximated analytically (the glows are already soft; the card's backdrop is the dot screen at its average cover). The file size is not stored on `MediaRef`, so the only content check is the hash (at most 2.5 MiB read per file). The slate uses Geist and Geist Mono when installed and falls back to system faces until they are bundled.

## 30. Loudness through the `ebur128` crate

- **Date:** 2026-09-30
- **Decision:** `media::analysis::loudness` measures with the `ebur128` crate (a Rust port of libebur128, MIT) instead of an in-house BS.1770-4 meter. Fixture references come from FFmpeg's `ebur128` filter and are matched within 0.1 LU integrated, 0.3 dB true peak and 0.5 LU loudness range.
- **Reason:** A maintained, reference-tested implementation of the standard; `cargo deny check` passes (it adds `bitflags` 1 beside 2, a duplicate warning only).
- **Consequences:** Loudness range differs from FFmpeg's by 0.3 to 0.4 LU on the stepped program fixtures (FFmpeg bins short-term values into a histogram); libebur128's values pass EBU Tech 3342, so the fixture tolerance is 0.5 LU rather than 0.1.

## 31. Project files: a versioned envelope, migrations on untyped JSON, newer files refused

- **Date:** 2026-09-30
- **Decision:** A project file is `{"format": "glass.project", "schema_version": N, "project": {...}}`. Loading migrates the `project` value one version at a time with pure `serde_json::Value` functions (`project::schema::migrate_vN_to_vN+1`), then deserialises the current model and validates it; saving always writes the current version. A file with a newer schema version is refused (`project.open_error.newer_version`), never read best-effort. Schema v2 stores `media` as `{"refs": [...]}` instead of a bare list.
- **Reason:** Migrating untyped values keeps only one set of model types (the current one) in the code, and each step stays small and testable. Reading a newer file would silently drop fields the newer build relies on, and saving it would destroy them. An object for `media` lets the media pool add its bins and metadata beside the references with a small, additive migration.
- **Consequences:** Every model change that alters the saved JSON bumps `SCHEMA_VERSION`, adds a migration and a `v<N+1>` fixture in `tests/fixtures/projects/`; old fixtures are never edited. `crates/project/tests/schema.rs` fails when `save` output changes without a fixture update.

## 32. Vector shapes by GPU coverage accumulation

- **Date:** 2026-09-30
- **Decision:** `render::shape` flattens curves and arcs to within 1/64 px and expands strokes into pieces that all wind the same way on the CPU, then rasterises outlines on the GPU by signed-area accumulation: every edge draws a quad from itself to the right edge of its outline's box and adds, per pixel, its height within the row times the fraction of the pixel to its right, with additive blending into an `R32Float` atlas. The sum is the winding number integrated over the pixel; non-zero clamps its magnitude, even-odd folds it. No tessellation crate (`lyon`) is used.
- **Reason:** Exact box-filtered anti-aliasing for straight edges without multisampling, both fill rules from one path, GPU work of about twice each outline's area regardless of its edge count, coverage that the mask node can reuse (`CoverageNode`), and no new dependency. Measured on the M2 (standing in for the M1): coverage within 2e-3 of exact polygon areas for straight edges and within 0.016 for curves; 50 mixed shapes into a 4K layer are reported in the Progress Log.
- **Consequences:** The fill rule applies to each pixel's integral, so a pixel where a twice-wound region meets an empty one (an inner stroke join, a pentagram's centre) is approximate (in the tests up to 0.06 at inner stroke joins and 0.35 at the inner corners of an even-odd pentagram). `R32Float` blending needs `wgpu::Features::FLOAT32_BLENDABLE`, which every Apple GPU has; when `app` sets up the shared device it should request it (otherwise `accumulation_format` falls back to `R16Float`, leaving about 1e-3 of coverage behind edges). Shape pipelines are built through `Renderer::custom_pipeline`, which other nodes with their own vertex stages can use.

## 33. Thread registry with seqlock accounting; decode pool of 2 to 4; thread-id for OS ids

- **Date:** 2026-09-30
- **Decision:** Every long-lived thread starts through `engine::threads::spawn`, which names it from its role and registers it; each entry's busy, idle and blocked totals are written only by the owning thread through a single-writer sequence counter over atomics, and the audio callback gets a pre-registered `AudioCallbackHook` that never allocates or locks. OS thread ids come from the `thread-id` 5 crate. The playback decode pool defaults to logical cores minus 3 (UI, render, audio decode with the callback), clamped to 2..=4. Render re-offers a frame to a full present queue every 2 ms instead of being woken by the presenter.
- **Reason:** The debug panel must read thread activity every frame without stopping threads, and the audio callback may not allocate or lock; a seqlock gives consistent copies with plain atomic stores on the writer side. Engine has no `unsafe` code, and `thread-id` (MIT or Apache-2.0, `libc`/`windows-sys` only) gives the id Instruments shows on macOS (`pthread_threadid_np`) and `GetCurrentThreadId` on Windows without allocating (the 0BSD `gettid` crate is outside `deny.toml`'s licence list). Four 4K software decoders stay near 0.6 GB on 8 GB machines, two are needed for a cut or transition, and the analysis pool pauses during playback. Render must not wait on the UI, so it cannot park on the present queue.
- **Consequences:** `shader-watch` (in `render`, which cannot depend on `engine`), `glass-crash-log` and `glass-file-picker` are named but not registered. `audio` stays free of Glass dependencies: engine hands it the hook as a closure. `thread-id` 5 brings a second `windows-sys` version on Windows (a `cargo deny` duplicate warning, not an error).

## 34. Master clock: callback frame counter, delay-locked loop, slewed output

- **Date:** 2026-09-30
- **Decision:** The master clock is the audio callback's frame counter, mapped to monotonic time by a second-order delay-locked loop (bandwidth 1.5 Hz narrowing to 0.1 Hz over a few seconds) fed with the monotonic time at callback entry plus cpal's reported output latency (playback minus callback timestamp; the buffer length when the host reports none). Readers never see the loop's estimate directly: the published line starts where the previous one is at each update and steers by changing its slope, by at most 0.5% of the rate. Only a gap over 100 ms re-seeds the loop. The presentation time is seconds on the stream's own timeline (frame over rate). Audio I/O uses `cpal` 0.18 (the Phase 0 default) and the callback's feed is an `rtrb` 0.4 ring; `cargo deny check` passes with both.
- **Reason:** Device crystals differ from the monotonic clock by up to a few hundred ppm and callback timing jitters by up to a millisecond, so neither the raw counter nor the last callback's timestamp is smooth enough for picking video frames. A DLL is the standard filter for this (JACK, PortAudio) and costs a few multiplications per callback. The monotonic reading at callback entry needs no mapping between cpal's per-host stream clocks and `Instant`; its cost is a constant lag of the mean wake-up delay.
- **Details:** `audio::drift`, `audio::Clock`, `audio::OutputStream`, `audio::OfflineOutput`; `crates/audio/tests/drift.rs` (0.1% fast and slow, 0 to 1 ms jitter, 256 to 1024-frame buffers), `crates/audio/tests/callback_alloc.rs`.
- **Consequences:** The scheduler owns the mapping from presentation time to timeline time (start offset, pause, shuttle) and subtracts `Clock::silent_frames` after underruns. Pausing the device re-seeds the loop on resume. `Clock::system` is the monotonic stand-in when no device is open; the offline backend covers tests and export. Video is slaved by `audio::video_sync::VideoSync`: the frame on screen at the middle of each refresh, with a 0.15-frame hysteresis band at boundaries, so device-to-display drift costs one repeated or skipped frame at a time and never touches the audio.

## 35. Rendered-frame cache: one LRU across VRAM and RAM, ceilings from the machine

- **Date:** 2026-10-01
- **Decision:** `render::frame_cache::FrameCache` keys frames by segment hash, frame index and a `RenderVariant` (size, quality step, settings hash), keeps one recency order across both tiers, spills VRAM evictions to RAM through a lossless `ReadbackRing` without waiting, stores them bit-exact by default (`SpillFormat::Srgb8` halves `Rgba16Float` frames as an option), and drops a frame whose spill cannot start. Default ceilings: a sixth of Metal's recommended GPU working set for VRAM, an eighth of physical memory for RAM (a sixteenth on unified memory), 1 GiB when the platform reports nothing. Physical memory comes from `objc2-foundation` (`NSProcessInfo`), already in the dependency tree.
- **Reason:** The plan keys by (segment hash, frame index) but adaptive quality renders the same frame at several sizes, which must not collide. Waiting for a spill would stall the render thread; dropping a frame only costs a re-render. Bit-exact spills keep cached and freshly rendered frames identical, which the deterministic-hashing rule relies on. Shares of the machine's memory leave room for decode, the compositor and the rest of the system on an 8 GB machine.
- **Consequences:** Phase 16's memory ceiling sets both ceilings at runtime (`set_vram_ceiling`, `set_ram_ceiling`). An `Srgb8` frame comes back as `Rgba8UnormSrgb`, so callers sample it rather than assume the original format.

## 36. LUTs: declared input space, tetrahedral interpolation in the shader

- **Date:** 2026-10-01
- **Decision:** `render::nodes::LutNode` applies a `.cube` LUT in the working space: alpha divided out, the working space converted into the LUT's declared input space (`render::lut::LutSpace`: Rec.709 display-referred by default, meaning BT.709 primaries and the inverse BT.1886 EOTF, a 2.4 power; sRGB; or linear light in the working primaries), the optional 1D shaper (linear interpolation) and the 3D table (tetrahedral interpolation), back to the working space, then mixed with the input by the intensity in linear light. Inputs outside a table's domain clamp to it, so HDR values above reference white clip in a display-referred LUT. The 3D table is an `Rgba16Float` 3D texture read with four `textureLoad`s and weighted in f32; the shaper is an `Rgba16Float` 2D texture in rows of 4096 entries. The `Renderer` binds an effect input as `texture_3d` when its texture is 3D (`EffectKey::volumes`). The project schema (`project::params::effects::lut`) stores the file as a path in a text parameter until the inspector has a file-pick row.
- **Reason:** Creative LUTs are almost all built for Rec.709 video code values, which is what the output node writes for SDR delivery, so the look matches other editors. Tetrahedral interpolation reads four entries instead of trilinear's eight, is exact on affine tables (identity included) and keeps the grey axis neutral; computing the weights in the shader avoids the 8-bit fixed-point fractions some GPUs use for hardware filtering of 3D textures, so the GPU matches the f64 CPU reference within f16 precision. f16 table entries are within 2^-11 relative, below one 10-bit code, at half the memory and bandwidth of f32.
- **Consequences:** Log input spaces (camera log curves) are added to `LutSpace` when the colour page needs them; their ids go into `project::params::effects::LUT_INPUT_SPACES` too (checked by `engine/tests/lut_ids.rs`). A 256-point table, the format's maximum, takes 134 MB of GPU memory; 33 and 65 points are 0.3 and 2.2 MB.

## 37. Portable mode: a `Glass Data` folder beside the executable

- **Date:** 2026-10-01
- **Decision:** Portable mode is on when a folder named `Glass Data` exists next to the executable; on macOS, when the executable is a bundle's `Contents/MacOS/` binary, next to `Glass.app` instead. In portable mode the config, data and per-user cache folders are `Glass Data/Settings/`, `Glass Data/Data/` and `Glass Data/Cache/`. `app::locations::Locations` is the only place that decides folders: each is the first writable candidate of its environment override (`GLASS_CONFIG_DIR`, `GLASS_DATA_DIR`, `GLASS_CACHE_DIR`), the portable folder, the platform folder (`dirs`), then `Glass` in the temporary folder. Environment overrides stay first because tests and developers rely on them. Falling back instead of failing keeps Glass usable from read-only media and from macOS App Translocation, which runs a quarantined app from a read-only random path.

A case is a scene per frame index (layers of procedural sources: NV12 bars through `YuvSourceNode`, uploaded stills, fills, text, vector shapes) rendered at 320 x 180 through `composite_stack` and `OutputNode::preview` with the frame index as the dither seed, compared with RGB golden PNGs. ## 39. Keymaps: one primary modifier, preset plus overrides, no sequences

- **Date:** 2026-10-01
- **Decision:** A chord is one key with `Cmd` (⌘ on macOS, Ctrl on Windows and Linux), `Ctrl` (the Mac Control key, folded into Ctrl elsewhere), `Alt` and `Shift`; shifted punctuation matches its base key with Shift. A keymap is stored as its preset's name plus per-command overrides (an override replaces that command's keys; an empty list unbinds it), as JSON with a format version, through `Keymap::load`/`save` at a path the app settings task chooses. No multi-key sequences: none of the four presets needs one. Presets give a command only the key the editor's published default list gives it, so commands an editor has no default for start unbound. Final Cut Pro's and Resolve's single trim key runs both ripple and roll trim and is not reported as a clash while neither command is changed. When two commands do share a chord, dispatch runs the one listed first in the registry and the editor flags the clash. The keyboard editor ships the board's window (keyboard map, key detail, changes, system keys, list with recording and clash resolution, Start from preset menu); switching preset keeps the user's changes on top (the board's default choice).
- **Reason:** One preset table then serves every platform, and storing only overrides lets a corrected preset reach users who never touched that command. Sequences would add a pending state to every key press for no preset's benefit.
- **Consequences:** The Switch preset dialog, saved sets, the preset comparison table and toasts on `Sheet / Keyboard`, and the Settings › Shortcuts pane, are follow-up sub-tasks. Sentences name chords in words (`Shift-S`) because the pinned snapshot fonts lack the modifier symbols, which keycaps draw as line icons; keycap labels use ‹ › where the board shows ◂ ▸ for the same reason.

## 40. Implicit gaps, per-kind tracks, markers in label colours

- **Date:** 2026-10-01
- **Decision:** A track stores only its items; gaps are the empty space between them, derived on demand (`Track::gaps`, `Track::item_at`), never gap items. Each track kind accepts one item kind: video and audio tracks hold clips, subtitle tracks hold subtitle cues, adjustment tracks hold adjustment items (`TrackKind::accepts`), and items on audio tracks sit on the sample grid, all others on the frame grid. Markers live on sequences (sequence time, frame grid) and on clips (source time, no grid), carry a start, a duration (zero for a point), a name, a note, a chapter flag, a to-do state and one of the five label colours (`media_pool::ColourLabel`, drawn in the clip theme roles), and are ordered by start then id.
- **Reason:** Stored gaps would carry no information the item ranges lack, yet every insert, remove, move and trim would have to create, split, merge or delete them and keep them in step with their neighbours, which is a whole class of invariant to get wrong. Source-time clip markers stay on the frame they mark when the clip is trimmed or moved. The design's marker popover offers exactly the label colours, and theme roles keep files free of RGB.
- **Details:** `project::model`, `project::marker`, schema v3 (`migrate_v2_to_v3`), autosave format 3 (`diff::Node::Marker`); `crates/project/tests/sequences.rs`, `crates/project/tests/schema.rs`.
- **Consequences:** Ripple and magnetic editing (Phase 6) compute gaps from item ranges. A clip marker outside the clip's visible source range is kept and not shown. A clip marker has no grid check because the project does not know source frame rates; the timeline snaps it when placing it.

## 41. Relinking: content hash decides, then weighted name and probe facts; one edit per batch

- **Date:** 2026-10-01
- **Decision:** `engine::media_mgmt::relink` walks the picked folders with the import scan and scores each file of the source's kind: an equal content hash is an exact match (100%, `Confidence::Exact`) whatever the name or folder; otherwise name similarity (case-insensitive stem, edit distance, containment) 0.35, duration 0.35 (a match within half a frame at the source's rate, at least 50 ms, scored by `1 / (1 + (Δ / 0.1 s)²)` so the nearer of two near-duplicates ranks first), resolution, frame rate and codec 0.1 each, over the parts both sides know, scaled by `0.6 + 0.4 × known weight`, times 0.9 when the hash is known to differ, capped at 95%. Tiers: Exact, Likely (at least 70%, picked for the user), Possible (40 to 70%, shown only). Every exact match's folder move (the paths without their common trailing components) is tried for the other offline sources. At most 2,000 files are hashed per search, the most likely first, and 8 are probed per source. A file shorter than the source range the clips use (less 1 ms) is listed but cannot be relinked, and `project::Project::relink_media` refuses it too. A batch is one `relink_media` edit (`EditLabel::Relink`) that replaces only `MediaRef` nodes, including the content hash.
- **Reason:** The content hash recorded at import is the one reliable identity (Decision 14), so it must outrank any name; a re-encode or proxy under the same name must never look identical. Names and lengths are what people recognise when the bytes changed. Repeating a move turns one found clip into a whole relinked card or drive. Replacing the hash keeps the next availability check from flagging a deliberately chosen re-export as changed.
- **Details:** `engine::media_mgmt::relink`, `project::relink`, `ui::dialogs::relink`; `crates/engine/tests/relink.rs`, `crates/project/tests/relink.rs`, `crates/ui/tests/relink_dialog.rs`.
- **Consequences:** Hashing reads up to 2.5 MiB per file, so a search of a large drive with no name or size hints may stop hashing before it reaches a renamed file; picking a narrower folder finds it. Relinking to a different file (hash changed) changes the analysis cache key, so its thumbnails and waveforms are recomputed.

## 44. Masks: shape coverage unioned, Gaussian feather, combined in list order before the blend

- **Date:** 2026-10-11
- **Decision:** A layer's masks (`render::mask::Mask`) are shapes in layer pixels, rasterised by `shape::CoverageNode` (each shape's interior with its own fill rule, strokes ignored) and unioned per mask (per-pixel max). A mask's feather is a separable Gaussian of standard deviation feather / 3, truncated at the feather (rounded up to whole pixels) and renormalised, clamping to the layer's edge, capped at 250 px; from 12 px the GPU blurs at half resolution and from 32 px at a quarter (2 x 2 or 4 x 4 averages, a Gaussian narrowed by the variance that averaging and the bilinear read back add), within about 1% of the full kernel away from the layer's border. Invert (1 - c) follows the feather. Masks combine in list order: the first starts the result, each later one by its mode, union (max) or intersection (min). `nodes::MaskNode` multiplies the layer's premultiplied linear-light colour by the result before the layer is transformed and blended; `mask::add_to_graph` adds the coverage nodes and the mask node between a layer's source and its `CompositeNode`. Mask textures are `R16Float`.
- **Reason:** Reusing `CoverageNode` keeps one rasteriser with exact box-filtered edges (Decision 32). A symmetric Gaussian keeps a straight edge at 0.5 where it was, so feathering does not grow or shrink the mask, and truncating at three sigma confines it to the stated radius; the separable form costs about one bilinear fetch per pixel of feather per pass (taps paired in one fetch), which at 4K made a 20 px feather on three shapes take 6.6 ms of GPU time at full resolution against 2.3 ms at half (M5, standing in for the M1). Max and min are the usual union and intersection of soft masks and keep 0..1 without clamping. Masking before the transform keeps the mask attached to the picture, like the crop (Decision 24), and multiplying premultiplied colour is how opacity already works.
- **Consequences:** Every shape costs a canvas-sized coverage pass and every feathered mask two blur passes, whatever the shape's size; a mask limited to the shapes' bounds is an optimisation for later. Subtract and difference modes, mask opacity and expansion (grow or shrink) can be added as further `MaskMode`s and fields. Parameters for masks in `project::params` come with the inspector's mask UI.

## 45. Clip properties: derived source range, a speed map of keys, centre-relative transform

- **Date:** 2026-10-11
- **Decision:** Schema v4 gives every clip a speed map, an enabled flag, gain in dB, a transform, a crop, opacity, a blend mode and an effect stack (`project::clip`). The timeline range (the item's `range`, on the track's grid) is stored; the source range is derived as `source_start` plus the timeline duration times the speed, exactly in rational time. An edit that derives a timeline duration from a source duration (`set_clip_source_range`, `set_clip_speed` keeping the source range) rounds it to the nearest whole grid step, halves away from zero, at least one step, and the source duration follows the rounded value; `trim_item` moves the source start by the head trim times the speed. The speed map is a list of keys (source time, speed) of which v4 holds exactly one at source time 0, a reduced positive rational from 1/100 to 100; reverse and freeze stay out until Phase 7. The transform stores position as the anchor's offset from the canvas centre in canvas pixels and the anchor as an offset from the layer centre in layer pixels, with per-axis scale (negative flips, up to 100 either way) and clockwise degrees, so the default (all zero, 100%) is `render::transform::Transform2D::centred` for any canvas and layer size; crop and feather are layer pixels as in Decision 24. Blend modes serialise as the `params::builtin::BLEND_MODES` ids. Each effect in the stack is a node with its own id from the project counter, the id of the `ParamSchema` its values follow, an enabled flag and `ParamValues` filled with the schema's defaults when added, and the stack applies first to last before crop, transform, opacity and blend. Every clip carries every property, whatever its track. Edit operations clamp numbers to their ranges and refuse non-finite ones; `Project::validate` refuses out-of-range values in a loaded tree. Autosave format 4 began with schema v4.
- **Reason:** Storing both ranges would let them disagree; the timeline range is the one that must sit on the grid, so it is primary and the other is exact arithmetic. A list of keys holds keyframed ramps later with the same JSON shape for constant speeds, so Phase 7 needs no data migration. The project knows neither the canvas nor the source picture size, so absolute pixel positions could not express "centred" for a new clip; centre offsets also survive a change of project resolution. Storing defaults in each effect keeps a saved look stable if a schema's default changes later. Keeping transform fields on audio clips and gain on video clips costs a few bytes and spares every edit a track-kind check and every track kind change a conversion.
- **Details:** `project::clip`, `project::model::Clip`, `project::schema::migrate_v3_to_v4`, `project::time::Time::round_to_multiple`; `crates/project/tests/clip_props.rs`, `crates/project/tests/schema.rs`, `tests/fixtures/projects/v4-*.json`.
- **Consequences:** The `params::builtin::transform` schema's position default (960, 540) and anchor (0, 0) are absolute pixels and uniform scale; the inspector's transform section must map to the clip's centre offsets and per-axis scale when it is wired to clips. Phase 7 ramps extend `SpeedKey` (an interpolation field with a serde default) and relax the one-key check, with a schema bump and an identity migration so older builds refuse those files as newer. Keyframe curves (Phase 5) animate `transform/position` and the other built-in section ids on top of these static values.

## 46. Vector shapes: sparse strips over the coverage accumulation

- **Date:** 2026-10-11
- **Decision:** Extends Decision 32. The signed-area accumulation stays exact and per pixel, but each edge's quad no longer runs to its outline box's right edge. `render::shape::strips` bins every outline on the CPU into bands of 4 canvas rows; in a band, the columns each edge crosses (`floor(min x)` to `ceil(max x)`, at least one) are merged into intervals, and the height of every edge in each row is added up left to right in f64 (the carry). An edge's accumulate quad covers its rows in the band from its first column to the end of its interval; paint pieces cover each interval (accumulation plus the carry of its row, then the fill rule) and each gap between intervals that the fill rule gives coverage (the carry alone, no atlas read); gaps left empty are not drawn. Pieces with the same columns and data that continue the band above are merged. `CoverageNode` draws the same paint pieces into its coverage texture instead of a full-canvas resolve. Carries within 1e-5 of a whole number are snapped to it.
- **Reason:** Right of every edge crossing a pixel row the row's winding integral is constant, so the accumulate quads only needed to reach the next edge. On the 50-shape 4K frame the old quads shaded 29.9 M blended accumulate fragments and 12.8 M paint fragments (9.3 ms GPU median on the M2, standing in for the M1); sparse strips shade 0.4 M and 5.3 M. On the M5 (machine shared with other agents), release: GPU median 1.72 ms before, 0.75 ms after; debug test profile: 1.7 to 2.6 ms median with a p99 up to 8.2 ms before, 3.45 ms median and p99 at most 7 ms after (the debug figure follows the slower CPU loop more than the GPU work). Coverage against the CPU reference and the visual regression goldens are unchanged. A tile-based winding scheme (per-tile backdrops, as in GPU path renderers) would need a compute pass and a second data path for masks; the strips keep the render-pass graph and the one fragment formula.
- **Consequences:** Binning moves work to the CPU: building the 50-shape node takes 1.6 to 1.8 ms in release (0.4 to 0.6 ms before), about 1 ms of it binning 25,749 edges, and 18.6 ms in the unoptimised test build (3 ms before). The accumulation atlas is written only inside intervals, so it means nothing without the paint pieces; any new reader (a mask node that wants raw winding) goes through `CoverageNode`. Paint is now one instance per piece (23,215 on the test frame) instead of one per outline.

## 47. Export encoder wrapper in `media::export`; native ProRes on macOS; GIF through the `gif` crate; AV1, VP9 and MP3 wait for the FFmpeg build

- **Date:** 2026-10-11
- **Decision:** The Phase 8 encoder wrapper is a new public module, `media::export` (`ExportSession`, `ExportSettings`, `VideoSettings`, `AudioSettings`, `Picture`), not a new crate: ARCHITECTURE section 2 already gives `media` encoding and muxing and `engine` the export pipeline, and `media` is the only crate allowed `ffmpeg-next`. - **Reason:** One module keeps the dependency rules and the `unsafe` boundary as they are. `allow_sw` keeps ProRes export working on the M1, which has no ProRes engine, with Apple's own encoder. FFmpeg's `aac` is the same on every platform (AudioToolbox's `aac_at` is macOS-only). The `gif` crate gives a per-frame palette without enabling another FFmpeg library.
- **Consequences:** The hardware encode task plugs `h264_videotoolbox`, `hevc_videotoolbox` and the others in through `VideoSettings::encoder` (any encoder of the same codec is accepted, except `prores_ks` without its flag). HDR exports carry colour tags only; mastering display and content light level metadata are left to the preset task. The fixture generator's VP9 clips also need `libvpx`, which the pinned build lacks.

## 48. Transitions: a folder per transition, a shared WGSL prelude, easing on the CPU

- **Date:** 2026-10-11
- **Decision:** A transition is a folder `assets/transitions/<id>/` holding `transition.json` (JSON, since `serde_json` is already a dependency and the project file is JSON: id equal to the folder name, i18n name key, category, offered directions from eight compass directions with the first as default, thumbnail progress, at most 8 parameters written as `project::params::ParamDef` JSON, text parameters refused) and `shader.wgsl`. `render::transition::TransitionRegistry` discovers them at startup (the source tree's folder in debug builds, copies embedded by the `assets` build script in release builds); a folder whose manifest or shader fails is reported and skipped. Every transition shader is compiled as `common.wgsl` + `transition.wgsl` + its own file and defines `@fragment fn fs`; the prelude fixes the bindings (uniform, sampler, A, B) and one uniform layout for all: eased progress, linear progress, direction index, direction unit vector, output size, then eight `vec4` parameter slots in manifest order (numbers in x, angles in radians, booleans 0 or 1, choices as the option index, points in xy, colours as straight linear RGBA). Easing is applied on the CPU before the uniform: linear, CSS ease-in `(0.42, 0, 1, 1)`, ease-out `(0, 0, 0.58, 1)`, ease-in-out `(0.42, 0, 0.58, 1)`, or any `cubic-bezier` (control x clamped to 0..1, y free to overshoot); every curve is exactly 0 at the start and 1 at the end. The shader name is `transition/<id>`; the shader library treats it as an external shader with a prelude, watched in its own folder in debug builds (Decision 19), and reloads every transition when the prelude changes. Thumbnails are not stored: the browser renders the transition at its thumbnail progress (`TransitionNode::thumbnail`).
- **Reason:** One fixed uniform and bindings make a new transition a single WGSL file with no Rust, which is what the 150-item library needs; 8 slots cover the plan's transitions (the widest, iris and shape wipes, need a shape, a centre, a softness and a colour). Easing on the CPU keeps it out of every shader and lets the timeline and the keyframe curve editor share one implementation. `render` cannot depend on `project`, so it keeps the definitions as JSON and reads only what it packs; the engine builds the `ParamSchema`, and a test there validates the bundled ones. Rendered thumbnails follow the current frame like the LUT browser's and add no binary files.
- **Details:** `crates/render/src/transition/`, `crates/render/shaders/transition.wgsl`, `crates/render/src/shaders.rs` (`add_external`), `crates/assets/src/transitions.rs`, `assets/transitions/README.md`; tests `crates/render/tests/transition.rs`, `crates/engine/tests/transition_schemas.rs`, visual case `cross_dissolve`.
- **Consequences:** A transition with more than 8 parameters, or a text one, needs the prelude to grow (a uniform layout change for every shader). Discovery happens once per process, so a new folder needs a restart; only shader edits hot reload. The timeline's transition items (Phase 5) store the id, linear duration, `Easing`, direction id and parameter values, and hand them to `TransitionNode`. Transitions from asset packs are discovered by calling `TransitionRegistry::discover` on the pack folder.
## 49. Look-ahead decode: one worker and one lane per segment

- **Date:** 2026-10-11
- **Decision:** `engine::lookahead` decodes ahead of the playhead across cuts and transitions as its own pipeline beside `engine::playback`'s skeleton. A `DecodePlan` (engine-local; `SegmentList` until a sequence-backed plan exists) lists `PlanSegment`s: source, timeline frame range, source time at the first frame, layer and the frame cache's `SegmentHash`. `glass-sched` hands each segment in timeline order to one idle `glass-decode-<n>` worker together with a new `spsc` lane of `depth` frames, whose consumer goes to `LookaheadFrames` (render's end) with a horizon message saying how far the plan has been handed out. The worker opens and seeks the source (pre-roll) and fills the lane with one frame per timeline frame (the last source frame at or before that instant), parking while it is full. At most `decode_workers + 1` lanes are open; at most `decode_workers` segments may overlap, and a segment that would exceed that is dropped with a warning. Depth defaults to as many 4:2:0 frames as fit 64 MiB (`LANE_BUDGET`), clamped to 2..=8: 8 at 1080p, 5 at 4K 8-bit, 2 at 4K 10-bit. `MediaDecoder` seeks with the playback decoder (`HwPreference::Auto`, `PreRoll::Steady`); `PreRoll::Software` (exact seek in software, hand-off to the hardware decoder's `seek_keyframe` at the next keyframe) stays available.
- **Reason:** Real decoders decode sequentially and seek expensively, so the skeleton's frame `n` to decoder `n % N` round robin would seek on every frame; one worker per segment decodes it in order, and a free worker pre-rolls the next segment while the current one plays. A lane per segment bounds decoded memory per stream and lets both sides of a transition decode at once. Measured on the M5 (shared with other agents; it stands in for the M1 reference) with `tests/lookahead.rs`: three cuts across two 1080p files (H.264 30 fps and HEVC 10-bit 25 fps), all mid-GOP, played against the system master clock with 60 Hz `VideoSync`: 0 late frames of 114 in all three set-ups, every cut ready 111 to 116 ms before its refresh (render pulls three frames ahead), pre-roll mean 42 ms with VideoToolbox, 38 ms in software, 51 ms with the software hand-off; 4K cuts inside one file: 145, 147 and 176 ms, 0 late. VideoToolbox was not slower to pre-roll than software here (the M2 handoff numbers were 51.5 vs 13.6 ms at 1080p), and the hand-off pays a second open and a GOP scan while short segments never reach hardware decode.
- **Details:** `engine::lookahead` (`mod.rs`, `plan.rs`, `media_decoder.rs`); `crates/engine/tests/lookahead.rs`.
- **Consequences:** The playback task that wires render replaces the skeleton's request rings with `LookaheadFrames` and builds the plan from sequences and clips (clip properties, speed). A run of segments each shorter than a pre-roll, more of them than there are workers, can still arrive late; the frame cache can skip decoding cached ranges later. On a machine whose hardware seeks are slow, switch the default to `PreRoll::Software` after measuring with the same test.

## 50. Dissolve family: dips by a midpoint, film in a 2.4 power curve, additive capped at max(white, brighter input)

- **Date:** 2026-10-11
- **Decision:** All dissolves work on premultiplied linear light in the working space and are exactly A at eased progress 0 and B at 1. Dip to black, white (1.0, diffuse white) and colour: A goes to the premultiplied colour by the `midpoint` parameter (5% to 95%, default 50%), then the colour goes to B; each half is a weighted sum with its weight clamped to 0..1, so an overshooting ease holds rather than extrapolates. Film dissolve: each straight (unpremultiplied) channel is encoded as sign(x)·|x|^(1/2.4) (the inverse of the BT.1886 power, odd so negative wide-gamut values and HDR values above 1 follow the same curve), the premultiplied encoded pictures are mixed by progress, and the result decoded with the 2.4 power; a pixel with zero alpha is treated as opaque. Additive dissolve: A weighted min(1, 2(1 − t)), B weighted min(1, 2t), summed, alpha capped at 1 and each colour channel capped at max(alpha, A·wa, B·wb). Non-additive dissolve: the per-channel (alpha included) maximum of the same weighted inputs. Film and non-additive return A and B themselves at 0 and 1.
- **Reason:** A display-like power is what makes a dissolve read as a film optical (the middle passes through the darker picture: black to white is 0.19 in linear light half way, not 0.5), and BT.1886's 2.4 matches the output encoding (Decision 21). Capping the additive sum at white keeps SDR pictures in range, and keeping the brighter input's value above white follows Decision 20 (highlights are neither clipped nor pushed further). An encode-decode round trip and a maximum against zero are not exact in floating point, so those two branch at the endpoints.
- **Details:** `assets/transitions/{dip-to-black,dip-to-white,dip-to-colour,film-dissolve,additive-dissolve,non-additive-dissolve}/`; tests `crates/render/tests/dissolves.rs` (f64 references), visual cases `dip_to_black` to `non_additive_dissolve`.
- **Consequences:** The film dissolve's curve is fixed (no gamma parameter). The dips share their WGSL function by copy, since a transition is one file over the shared prelude.

## 51. Hardware encode: an encoder preference with fallback on open and on the first frames

- **Date:** 2026-10-11
- **Decision:** `media::export::VideoSettings` gains `encoder_preference: EncoderPreference::{Auto, Hardware, Software}`, `Auto` by default, the same three-way choice as `ProxyEncoder`. `Auto` tries the platform's hardware encoders for H.264 and HEVC (`*_videotoolbox` on macOS; `*_nvenc`, `*_qsv`, `*_amf` in that order on Windows and Linux; ProRes keeps `prores_videotoolbox`) and then `libx264` or `libx265`; `Hardware` never falls back; `Software` skips them; codecs without hardware encoders ignore it; `VideoSettings::encoder` still names one encoder with no fallback. Hardware encoders get NV12, or P010 for 10-bit settings (HEVC Main 10; hardware H.264 is skipped for anything over 8 bits), and a constant quality mapped from the CRF (the software default, 23 or 28, for `RateControl::Default`): VideoToolbox `-q:v` = 100 - 1.75 x CRF (CRF 23 gives 60, near x264 CRF 23 in PSNR and size), NVENC `rc vbr` with `cq`, Quick Sync ICQ `global_quality`, AMF `cqp` with `qp_i/p/b`; the preset goes to software encoders only. An encoder that fails to open is replaced at `ExportSession::create`. One that opens stays on trial until its first packet (at most 8 frames): the session keeps the frames it sent and adds no muxer streams yet (audio packets wait), and an error from sending or receiving replaces it with the next encoder, the frames converted with `FrameScaler` when the pixel format changes and replayed, so the file holds only the replacement's packets. `ExportSummary::{video_encoder, fallbacks}` and `ExportSession::fallbacks` report what ran and what was given up on, with FFmpeg's reason. The NVENC, Quick Sync and AMF names, formats and rate options are selected with `cfg!` so they compile on every platform, but they are not verified on hardware (needs-human).
- **Reason:** Speed comes first (Decision Log, 2026-09-29), and VideoToolbox encodes several times faster than x264 and x265 at a similar quality, so `Auto` is the default. A hardware encoder can fail where software never does (picture sizes beyond its limits, a busy or missing GPU, a driver without the codec), and most failures show at open or on the first frame, so those two points are covered without buffering more than a few frames. Constant quality keeps hardware exports from FFmpeg's 200 kbit/s default bit rate and lets one CRF setting drive both kinds of encoder.
- **Consequences:** The same settings can produce different bitstreams on different machines; tests that need a fixed encoder set `Software` or name it. A hardware encoder that fails after its first packet fails the export, as a software one does. VideoToolbox takes colour tags from the frames, which the session's converter sets. Verifying NVENC, Quick Sync and AMF (encode, fallback, tags, quality mapping) needs Windows or Linux machines with those GPUs.

## 59. Output verification: findings as i18n keys, hard bounds fail, soft bounds warn

- **Date:** 2026-10-11
- **Decision:** `media::export::verify::verify` re-reads a finished export against its `ExportSettings`, the expected frame count and duration, and the preset's loudness target and platform limits. Frames are counted from the video packets, not the container's count; video duration must be within one frame, audio within one coded audio frame (1024 samples for codecs without a fixed frame size), and the audio is decoded at its own rate through `AudioReader` into the analysis loudness meter for integrated loudness and true peak, compared at the 0.1 LU and 0.1 dB they are shown with. ## 52. Adaptive quality: a pure governor in render, resolution first, drops only at a quarter

- **Date:** 2026-10-11
- **Decision:** `engine::quality::QualityGovernor` is a pure state machine fed one `FrameTiming` per presented frame (budget: one frame interval of the clock; decode lateness: how long render waited for the frame's decoded input while playing; render time). Levels are full, half and quarter of the canvas per axis (`QualityLevel::preview_size`); reduced levels also cap the composite's resampling at bilinear (Decision 23) and key cached frames by `cache_step` in `RenderVariant::quality` (Decision 35). It steps down one level at once on two misses in a rolling 12-frame window, or when a full window averages under 10% headroom; it steps up one level after one second of frame time with no miss and at least 35% mean headroom in the window; the window restarts at every change. A step up that steps back down within a second doubles the wait before the next step up to that level, up to 16 s. `admit` drops a frame only at the quarter level, when the last frame there still missed and the frames have fallen a whole interval behind the clock; each drop catches up one interval. Playback stopping restores full resolution at once and forgets the history and back-off. In `engine::playback`, render asks `admit` before each frame, passes the level to `Render::render` (the hook where the preview graph is built), reports the timing and publishes counters (`Playback::quality`: frames, misses, steps down and up, restores, drops, level); while the level is reduced it waits for input with a one-interval timeout, and when that expires with playback paused it restores full and offers `Render::rerender` the frame on screen.
- **Reason:** A deterministic state machine can be tested on synthetic timelines of costs, separate from threads and timers. Two misses (not one) keep a single hiccup from costing resolution; a 10% to 35% band with a one-second hold keeps steady borderline load from flickering between levels (a minute of 12% to 33% headroom changes nothing), and the back-off turns a level that can never hold from a probe every second into ever rarer probes: a minute with full at 120% of the budget and half at 30% makes 6 step ups (13 changes; 49 without the back-off). Decode lateness counts in the cost though a smaller preview does not decode faster, so a decoder that cannot keep up walks the level down to where frames drop, which is what a decode-bound stream needs. The skeleton has no clock yet, so the budget is the frame interval and render measures its own wait and render time; the restore needs a timed wait because nothing else wakes render when playback pauses, and it only times out while the level is reduced.
- **Details:** `engine::quality`, `engine::playback` (`Pacing`); `crates/engine/tests/quality_governor.rs`, `crates/engine/tests/adaptive_quality.rs`. Headless playback at 100 fps (debug, M5 standing in for the M1, machine shared with other agents): render at 24.5 / 6.5 / 2 ms per frame for full / half / quarter stepped down at frame 2 and dropped none of 151 frames; at 30 / 18 / 15 ms it showed 2 full, 2 half and then quarter frames, dropped the first frame at 5 (after the quarter level began at 4), 61 of the first 121, and after the pause re-rendered the frame on screen at full.
- **Consequences:** The playback task that wires the master clock and `LookaheadFrames` replaces the budget with the deadline minus the frame's start and the input wait with `next_into_timeout`'s wait. A real `Render` builds its graph at `preview_size` and upscales for display, and implements `rerender` by keeping the last frame's decoded textures. Full resolution during playback still uses the renderer's own filter choice; reduced levels force bilinear.

## 53. Scrub mode: nearest cached frame at once, exact frame in software after a 40 ms pause

- **Date:** 2026-10-11
- **Decision:** `engine::scrub::Scrubber` is owned by the UI thread while the playhead is dragged. `request(frame)` never waits: it replaces the worker's pending request in a one-slot `ArrayQueue`, unparks `glass-scrub` and answers from `CachedFrames` (the timeline frames resident in the rendered-frame cache at the current variant, kept by whoever fills or evicts the cache) with `try_read` only: the requested frame when cached, else the nearest cached frame, where the frame on the side the pointer moves toward wins unless it is more than `ahead_bias` (2) times as far as the one behind, else the frame on screen (also when a writer holds the index). Repeating the last frame is not a new request. When the latest request is `pause` (40 ms) old on the `ScrubClock`, the worker decodes that timeline frame exactly: every covering `PlanSegment` of the look-ahead's `DecodePlan`, one `ScrubDecoder` per source opened on first use and kept until the scrub ends (`SoftwareScrubDecoder`: `HwPreference::Off`, shared `GopIndexes`, the GOP walked as exact seeks 100 ms of source time apart so it can stop between steps), renders it into the cache through `ScrubRender`, adds it to `CachedFrames` and publishes a `Ready` through a second one-slot queue; a cached frame is published without decoding. A newer request cancels the exact decode (between steps and layers); a frame finished for an older request is neither rendered (if not yet) nor published, and `poll_ready` drops stale answers. While requests keep coming the worker prefetches cheap frames: the first timeline frame showing each source keyframe within `prefetch_window` (90) frames ahead in the direction of motion, nearest first, at most `prefetch_per_move` (2) per request, single-layer, uncached and untried only, cancelled when the pause runs out. `finish` stops and joins the worker, cancelling its decode, drops the decoders and returns the last requested frame for playback.
- **Reason:** The UI must never wait (lock-free queues, an unpark and a `try_read`). Exact seeks were 3 to 4 times faster in software than with VideoToolbox on the M2, and VideoToolbox seek landing is under investigation on the M5, so scrubbing decodes in software and playback keeps the hardware decoder. A frame showing a keyframe decodes with no GOP walk, so prefetching those keeps a near frame in the cache for little work. Measured on the M5 (shared with other agents, standing in for the M1; debug test build, the two media tests running at once) with `tests/scrub_media.rs`, 60 random uncached frames each: time from the end of the pause to the exact frame median 15.3 ms, p95 21.9 ms at 1080p, 26.5 / 54.7 ms at 4K (first request with open and GOP index 23.8 / 50.0 ms); a synthetic scrub at 3 frames per 8 ms pointer event (12.5x real time) from an empty cache answered 88% (1080p) and 87% (4K) of requests within 15 frames, median 9 frames away, with 35 and 23 frames prefetched; without prefetching nothing was answered.
- **Details:** `engine::scrub` (`mod.rs`, `cached.rs`, `clock.rs`, `decoder.rs`), thread role `Role::Scrub` (`glass-scrub`); `crates/engine/tests/scrub.rs` (manual clock, made-up decoder), `crates/engine/tests/scrub_media.rs`.
- **Consequences:** The playback task that wires render implements `ScrubRender` by sending the layers to `glass-render` and waiting for the cached frame, keeps `CachedFrames` in step with the cache's inserts, evictions and variant changes, pauses the analysis pool and the look-ahead while scrubbing, and seeks playback to `ScrubEnd::frame`. A single exact seek inside FFmpeg cannot be interrupted, so cancelling waits for at most one 100 ms step. The clip model hook replaces `SegmentList` as the plan. The scrub latency benchmark (Phase 3) can reuse `tests/scrub_media.rs`.

## 54. Transitions in the project: nodes on a track's cuts, refused edits, fitted neighbours, head handles only

- **Date:** 2026-10-11
- **Decision:** Schema v5 gives every track a list of transitions (`project::transition`), ordered by id, each a node with its own id from the project counter naming the outgoing clip (ending at the cut) and the incoming clip (starting there). Either side may be empty next to a gap or the track's start, for a fade from or to nothing; such a one-sided transition is refused (`CutNotFree`) where its clip's edge meets another item, which takes a two-sided one. Each clip edge holds at most one transition and a track's transitions never overlap. Only clips take transitions (video and audio tracks). A transition stores the render-side kind id (`assets/transitions/<id>/`, lowercase letters, digits and `-`, default `cross-dissolve`; unknown kinds are kept), its duration as a positive whole number of the track's grid steps, an alignment (`centre`: the extra step of an odd duration after the cut; `start`: starts at the cut, over the incoming clip, needing the outgoing clip's media past its end; `end`: ends at the cut, over the outgoing clip, needing the incoming clip's media before its start), an optional direction id from the kind's offered directions (Decision 48; `None` is the kind's default, kept when the kind changes), an easing id (default `linear`; the engine maps `linear`, `ease-in`, `ease-out` and `ease-in-out` to Decision 48's curves) and `ParamValues` for the kind's schema (cleared when the kind changes). The span must stay within its clips (or the gap), at or after zero, off the neighbouring transitions and within the incoming clip's head handle, its source start over its speed. Edits on a transition (add, duration, alignment) refuse a span that does not fit with `TransitionRoom` (side, needed, available) or `TransitionHandle` (clip, needed, available, in timeline time) and never clamp. Edits on items (insert, delete, move, trim, and slip, speed and source range changes) then fit the track's transitions in cut order: one whose clips no longer meet at its cut, whose clip left the track, or whose one-sided edge now meets an item is removed; one that no longer fits is shortened to the longest whole number of grid steps that fits, and removed when not one step does; when two compete for one clip or gap, the earlier keeps its length. Tail handles (media past the outgoing clip's end) are not checked by edits or validation, because the project does not store media lengths: `Project::check_transition_media` checks them against lengths the caller supplies (the media pool's facts), and `source_used_until` includes them, so relinking refuses a file too short for them. The engine's query `Track::segment_at` returns one item or the transition holding the time with both clips, its span and linear progress `(time − start) / duration` (0 at the first instant, below 1 at the last; easing not applied). New undo labels: Add Transition, Delete Transition, Change Transition Duration, Align Transition, and Change Transition (kind, direction and easing). Autosave format 5 began with schema v5.
- **Reason:** Naming the clips keeps a transition attached to its cut through edits elsewhere and lets a fade travel with its clip; storing the cut time as well would duplicate what the items already say. Refusing direct transition edits shows the user the limit instead of silently giving a different length, while refusing a trim or slip because of a transition would block ordinary editing, so those edits shrink or drop it, the way most editors behave. Fades from and to black at the start and end of a programme are common enough to need no extra clip. The head handle is source time 0, which the tree knows; media lengths live in the media pool, outside the tree, so checking tail handles in every edit would need the pool inside `project`'s edits or a duplicate length per reference that relinking would have to keep in step. Linear progress at the instant asked keeps the query exact and lets the engine pick the sampling instant and apply the easing curve.
- **Details:** `project::transition`, `project::model::Track::transitions`, `project::schema::migrate_v4_to_v5`, `project::diff::Node::Transition`, `project::time::Time::floor_to_multiple`; `crates/project/tests/transitions.rs`, `crates/project/tests/schema.rs`, `tests/fixtures/projects/v5-*.json`.
- **Consequences:** A roll edit (moving a cut with its transition) must be one edit that moves both clip edges, or the transition is removed by the first trim. The transition browser's default duration and "apply to all cuts" (Phase 9) go through `add_transition`. Custom cubic-bezier easing curves need more than an id: the easing editor (Phase 9) adds them with a schema bump; the engine treats an unknown easing id as linear until then.

## 56. Frame queues park on their own mutex-and-condvar parker

- **Date:** 2026-10-11
- **Decision:** `engine::frame_queue` replaces `crossbeam-utils`' `Parker` with a small private parker (a wake-up token in a `std::sync::Mutex<bool>` and a `Condvar`). `Parker::new` locks the mutex, waits on the condition variable with a zero timeout and notifies it once, so the standard library allocates both there. `crossbeam-utils` is no longer a direct dependency (amends Decision 27).
- **Reason:** On macOS the standard library allocates a mutex and condition variable on first use. The old warm-up (`park_deadline(now + 1 µs)`) could return before it reached the condition variable when the thread was preempted, so the first real wait allocated: `frame_queue_alloc` failed 48 of 300 runs under 12 parallel copies. With the new parker it failed 0 of 1,800.
- **Consequences:** `unpark` always takes the parker's mutex. That costs nothing extra on the hot path, because a side only unparks the other after seeing its waiting flag.

## 60. Timeline playback: segments from the sequence, one graph per frame, deadlines from the clock

- **Date:** 2026-10-11
- **Decision:** `engine::timeline::TimelinePlan::build(project, sequence)` turns the video tracks, bottom first, into look-ahead `PlanSegment`s: one per enabled clip, its source start and constant speed carried (`PlanSegment::speed`; the look-ahead and the scrubber step the source by the frame duration times the speed), its range stretched over the head and tail handles its transitions show, from `Project::transition_needs`, so a transition is two overlapping segments. A segment's hash covers its item id, media, timeline range, source start and speed. The plan also lists, per timeline frame, each track's clip or transition (with the linear progress `Track::segment_at` defines), and splits the timeline into runs of frames compositing the same things; a run's hash (clip looks, transition settings, segment hashes, bottom to top) is the frame cache's `SegmentHash`, with the absolute timeline frame as the frame index. `TimelineRenderer`, owned by `glass-render`, renders one graph per frame at the sequence's canvas (`TimelinePlan::canvas`, the schema v6 resolution), scaled by the preview quality: `YuvSourceNode` (the source's gamut matrix is folded into it, so every source path converts primaries without a separate `GamutNode`), LUT effects, then crop, transform, opacity and blend as a composite layer; a transition places each side alone on a transparent canvas and mixes them in a `TransitionNode`, unknown kinds falling back to the cross dissolve; reduced levels cap resampling at bilinear (Decision 23); the 8-bit preview output, dithered with the frame number as seed, is cached and presented. `TimelinePlayback` replaces the skeleton's per-frame round robin: render takes every frame in order from `LookaheadFrames`, asks the governor, renders and waits for the GPU, and queues a `PresentedFrame` with its due time on the master clock: the first frame after play or seek is due when ready, frame `t` one interval per frame later; the governor's budget is the time from when render could start the frame to that deadline, at most one interval, and its decode lateness the time render waited for the look-ahead; a frame finishing after its deadline is late. Scrubbed frames go to `glass-render` through `TimelineScrubRender` into the same cache, and `CachedFrames` holds the full-quality frames resident, dropping those the cache lets go of.
- **Reason:** One path from project to presented frame keeps playback, scrubbing and the later export identical frame for frame (the test checks played frames against single-frame renders bit for bit). Hashing segments by their own clip and runs by what they composite makes an edit invalidate only the frames it changes, which the dirty-range task needs. Anchoring deadlines at the first ready frame keeps a seek's pre-roll from counting as lateness, and capping the budget at one interval keeps a renderer that runs ahead of the clock honest about throughput.
- **Details:** `crates/engine/src/timeline/` (`plan.rs`, `render.rs`, `playback.rs`), `crates/engine/tests/timeline_playback.rs`. The working space is still the renderer config's (BT.709 by default), not yet the project settings' working primaries; masks wait for a mask field on clips; offline sources draw nothing yet (no slate); the look-ahead still decodes frames that the cache already holds; the plan is fixed for a playback session (an edit restarts it with a new plan). The `engine::playback` skeleton remains for its thread-layout and adaptive-quality tests.
- **Consequences:** The app creates a `TimelinePlayback` per sequence, shows `PresentedFrame`s by their due time, and starts a `Scrubber` with `plan.segments()`, `cached_frames()` and `scrub_render()`, calling `show(frame)` for its answers. `smoke` can play the reference project through `TimelinePlayback` once `tests/fixtures/reference.proj` exists.
## 57. Hardware decoders are reopened on every keyframe seek

- **Date:** 2026-10-11
- **Decision:** `FrameReader::reset_decoder` reopens a hardware decoder after every keyframe seek, `seek_keyframe` and `seek_to_start`, instead of flushing it (before, only a drained one was reopened). Software decoders are still flushed, and a target ahead in the current GOP still decodes forward without any reset. The look-ahead's `MediaDecoder` gets this through the reader, for steady seeks and for the hardware decoder's keyframe seek in the `PreRoll::Software` hand-off.

- **Details:** `crates/media/src/reader.rs`; tests `crates/media/tests/seek.rs` (`hardware_seeks_match_linear_decode`), `crates/media/tests/seek_open_gop.rs`, `crates/engine/tests/lookahead_open_gop.rs`. `tests/fixtures/generate.sh` pins x264 to `threads=16`, because x264's default thread count follows the core count and changes the bitstream; with 16 the open-GOP fixture exposes the bug on every machine. ## 61. Wipes: coverage of a moving edge in output pixels, filtered by one kernel, with margins for softness and border

- **Date:** 2026-10-11
- **Decision:** Every wipe computes B's coverage per pixel from a signed distance in output pixels (from `tr.size`) to its moving edge, through one kernel: a 1 px box when the softness is 0 (analytic anti-aliasing of a straight edge), widened to the softness and eased towards a smoothstep as the softness passes 1 px. The optional border is the band between B's edge and the same edge moved the border width towards A, in the border colour (straight linear RGBA, premultiplied). Each edge starts and ends a margin (half the kernel plus the border) outside the frame, so softness and border slide in and out without a jump, and every shader returns A and B themselves at progress 0 and 1. Softness and border width are output pixels, like crop and mask feathers (Decisions 24 and 44). Shapes: linear wipe (one transition, 8 manifest directions, diagonals at 45 degrees); radial wipe (a circle from a centre point given as a fraction of the frame, possibly outside it); clock wipe (a hand turning once from a start angle, clockwise or anticlockwise, around a centre point; arc lengths measured at a radius of at least twice the margin and the hand starting and ending that margin beyond the start ray, so the softness stays bounded at the centre; the start ray is anti-aliased but never softened, and the border follows the hand only); iris (circle, diamond, rectangle of the frame's aspect, five-pointed star with inner corners at 0.45 of its radius, centred, opening or closing, as exact signed distances that shrink to a point and keep receding); barn door (vertical or horizontal split, opening or closing); venetian blinds (count, 4 directions); checker wipe (columns by rows, 4 directions; one checker colour wipes in the first half and the other in the second). Blinds and checker cells sum the kernel over each interval of B in the cell and its neighbours (along and across), which filters the hard mask exactly with the softness capped at the cell size, so cell boundaries are anti-aliased and full cells join without a seam; their border narrows near the start and end of a cell's wipe.
- **Reason:** One kernel in pixels gives the same edge quality across shapes and resolutions, and coverage that is non-decreasing in progress by construction (each edge only moves towards A), which the tests check pixel by pixel. Summing the kernel's cumulative function over intervals avoids the seams and popping that a per-cell local coordinate gives at cell boundaries. A radial wipe with a free centre and a centred iris with more shapes keep the two distinct.
- **Details:** `assets/transitions/{linear-wipe,radial-wipe,clock-wipe,iris,barn-door,venetian-blinds,checker-wipe}/`, category `wipe`; tests `crates/render/tests/wipes.rs` (endpoints, monotonic coverage, f64 references for the linear and checker wipes, placements, 4K timing); visual cases `linear_wipe` to `checker_wipe`. The visual harness's `Source::Transition` gained a `setup` function for directions and parameters.
- **Consequences:** The edge kernel and composite were first copied into each wipe's shader; they moved into the prelude `transition.wgsl` with the motion transitions (9d1ace7, Decision 62). A proxy at a lower resolution needs softness and border scaled by the caller. The clock's start ray shows the border's hard edge only along the hand, and a border on blinds and checker cells is at most the remaining travel.

## 67. Dirty ranges from the project diff, cache keys by content, no eviction on edit, plans swapped between frames

- **Date:** 2026-10-11
- **Decision:** `engine::timeline::DirtyRanges::between(old, new)` is a pure function over `project::diff`'s records: a changed item on a picture track (video, subtitle, adjustment) dirties its old and new extents plus the spans of the transitions naming it in either root; a transition its old and new spans; a changed media reference every clip using it; a track added, removed, or changed in anything but its name its whole content in both roots (and, when the picture tracks change order, every track whose place among them moved); a sequence added, removed, or changed in anything but its name, drop-frame flag, sample rate and channel layout every frame; project settings changed in anything but the default sequence format and cache folder every frame of every sequence. Markers (sequence or clip), names and audio tracks dirty nothing. A nested sequence's dirty frames (Decision 69) carry up to every sequence with a clip of it, mapped through the clip's source start and speed and kept within the clip's extent and its transitions' spans, repeated up the nesting (all of the clip when the speed does not resolve or every child frame is dirty). Fields a later schema adds to a track, sequence or the settings are compared too, so they count as changing everything they cover until listed. A clip's frame cache key (its look hash within `TimelinePlan::span_hash`) covers the media and the source time at timeline zero instead of the decode segment (whose hash keeps the range), so trimming either end or stretching a clip over a transition's handle keeps the keys of the frames it still shows. Edits evict nothing: cache entries are keyed by content, so changed frames miss, and stale entries age out of the LRU order while an undo hits them again; only the `CachedFrames` index is brought in step over the dirty frames. `TimelinePlayback::set_plan(plan, dirty)` (refused with `FormatChanged` for another canvas or rate) hands the plan to `glass-render`, which swaps it in between two frames, re-presents a dirty frame on screen while paused and calls `LookaheadFrames::replan`: the scheduler keeps every lane whose segment hash the new plan has (unless it skipped frames inside the dirty ranges), drops the rest and hands out the new plan from render's position, and the consumer holds frames back until the replan's epoch comes back. Look-ahead workers skip decoding runs of frames `CachedFrames` lists when the run reaches the segment's end or lasts at least 2 s (`SKIP_MIN_SECONDS`), queuing `Layer::skipped` frames and seeking at the next uncached frame; render answers them from the cache (falling back to the full-quality frame at a reduced level), and when the cache let go of one meanwhile it calls `LookaheadFrames::refill`, which re-hands that frame's segments from it. The `engine::playback` skeleton is deleted: `default_decode_workers` moved to `engine::lookahead`, and its thread-layout and adaptive-quality tests run `TimelinePlayback::start_with` with a `FrameRender` stand-in and made-up decoders (`crates/engine/tests/stand_in/`). Moving them found two faults in `TimelinePlayback`, fixed here: the governor's budget is one frame interval again (Decision 52) instead of Decision 60's time left to the deadline, which was zero once render fell behind, so `admit` never dropped and playback fell further behind for good (30 / 18 / 15 ms per frame at 100 fps: 119 misses, no drop; now drops start after the first quarter frame); and a seek while playing kept dropping a pending frame that already belonged to the new position.
- **Reason:** The project diff already compares nodes by pointer, so the cost follows the edit, and comparing whole records with the known render-free fields normalised away cannot miss a new kind of edit. Keys by content make correctness independent of the dirty ranges (a frame renders again exactly when what it composites changed), so the ranges only need to be a superset; keeping stale entries costs nothing until memory is needed and makes undo free. Keeping lanes by hash keeps decoders positioned through looks-only edits, the common case while tweaking. A seek costs at most a GOP of decoding, so skipping only runs longer than a typical GOP (or reaching the segment end, needing no seek) never costs more than decoding through; the refill path keeps a cache eviction between the worker's decision and render from ever showing a wrong or empty frame. The project has no track visibility flag yet (Phase 6 track headers): the test hides V2 by turning it into an audio track, which removes its pictures the same way.
- **Details:** `crates/engine/src/timeline/dirty.rs` (unit tests per edit kind), `plan.rs` (content look hash), `playback.rs` (`FrameRender`, `start_with`, `set_plan`, refill), `render.rs` (`reindex_dirty`); `crates/engine/src/lookahead/mod.rs` (`replan`, `refill`, skipping, `frames_skipped`); `crates/engine/tests/dirty_range.rs`.
- **Consequences:** The app builds the new plan and the dirty frames on each edit and calls `set_plan`; a scrubber started before the edit keeps the old segments and is restarted. When keyframes reach the plan, an animated clip's look hash must include its evaluated values per frame (spans of one frame where values change), so a key edit misses only the frames whose values changed. A new canvas or frame rate needs a new `TimelinePlayback`.

## 64. Timing tests: serial sections, thread CPU time, load-robust statistics by default, the strict ones under `GLASS_STRICT_TIMING=1`

- **Date:** 2026-10-11
- **Decision:** Every timing test goes through one helper, `crates/render/tests/common/timing.rs`, included by path by the `ui` and `engine` tests. A timed section holds a process-wide mutex (`timing::serial()`), so the timing tests of one binary never overlap. CPU sections (UI frames, a submit, a send) are timed on the wall clock and on the thread's CPU clock (`clock_gettime(CLOCK_THREAD_CPUTIME_ID)` on macOS and Linux; Windows has no clock fine enough, as `GetThreadTimes` moves by the 15.6 ms tick, so the wall time stands in). By default the medians on both clocks are held to the budget and the test's own statistic (p99, max) of CPU time to 2x it; wall-only figures (frame lateness, decode frame times) to the budget at the median; GPU pass times to 1.5x the budget at the fastest tenth and 3x at the median. With `GLASS_STRICT_TIMING=1` each test's own statistic is held to the budget itself, as before: the p99 or max on both clocks, the GPU median, the mean decode time (60 fps). CI's macOS arm64 job runs the timing tests again in a strict step, one test at a time. UI frame tests use `ui` test support `FrameBudget` (two `FrameTimeMonitor`s); `ui::headless` is unchanged.
- **Reason:** Measured on the M5 (shared with other agents) with ten busy-loop processes plus the visual regression and 4K composite tests looping: UI wall-clock p99 reached 22.5 ms against 8 ms (quiet at most 4.6 ms), while the CPU p99 reached 10.0 ms and the medians 5.2 ms (wall) and 4.2 ms (CPU): a busy machine slows a thread's own work about twofold but its median stays under budget. GPU pass times are bimodal on a quiet machine too, from the GPU's clock: the 4K cross dissolve took 1.27 ms or 2.2 ms per pass in stretches of a few dozen frames in the same process, and was faster under GPU load (1.46 ms median) than quiet (2.26 ms), so rerunning alone did not help; a 150 ms busy warm-up did not pin the clock, and submitting extra passes before the timed one inflated its timestamps to 4.6 ms. The fastest tenth stayed within 1.01x of the budget quiet and loaded. All 22 timing test binaries passed quiet and five rounds under that load. In the default mode, a 10 ms spin or sleep in every measured CPU section (20 ms per decoded frame, 50 ms per delivered playback frame) failed all 14 CPU-timed tests, and a shader loop adding 7.8 to 11.3 ms per 4K pass failed all 8 GPU-timed tests (a 6.2 ms addition to the 50-shape pass, 9.6 ms against its 8 ms budget, passed: it fails only the strict check).
- **Details:** Converted: the ten `ui` frame-budget tests, `render` `cross_dissolve_at_4k_gpu_time`, `dissolves_at_4k_gpu_time`, `wipes_at_4k_gpu_time`, `output_pass_at_4k_gpu_time`, `lut_pass_at_4k_gpu_time`, `five_4k_layers_gpu_time`, `five_transformed_4k_layers_gpu_time`, `fifty_shapes_4k_gpu_time`, `submit_never_waits_for_the_gpu` (and `readback_4k_throughput_and_latency` serialised), `engine` `submitting_never_waits_for_a_write`, `h264_4k_hardware_throughput`, `three_cuts_across_two_files_play_with_no_late_frames_at_1080p` (and the 4K cut report serialised). Report-only timings (mask, text, frame cache, scrub) are unchanged. CONTRIBUTING.md "Timing tests".
- **Consequences:** Default runs catch a regression of about a frame budget (a frame that costs 8 ms more, a pass that doubles) but not a 20% slowdown; that is the strict step's and the benchmarks' job. The strict GPU medians still swing with the GPU clock, so the strict CI step may need its GPU warmed or its budgets reviewed once CI runs. A failing default-mode timing test is a regression, not load, and is not rerun to get a pass.
## 62. Motion transitions: moved frames over transparent black, blur by taps in one pass

- **Date:** 2026-10-11
- **Decision:** The motion transitions map each output pixel back into the moved frame (A's output pixels; B stretched to the same size) and sample it filtered through the clamping sampler, weighted by the frame's coverage, a 1 px box at its edges in output pixels (scaled by the frame's footprint when it is scaled), so whatever a moved frame leaves uncovered is transparent black and nothing wraps. Push moves A and B edge to edge by a frame (left, right, up, down); slide lays the moving frame over the still one (`over`; in: B over A, out: A off B); whip pan is a push on a quintic smootherstep, box-blurred along the direction by the blur parameter's fraction of the frame at the peak speed and in proportion to the speed elsewhere, from up to `samples` evenly spaced taps of A and B edge to edge (each extended by the clamping sampler, so a flat picture keeps its level; staggered per row across the direction when the taps are more than a pixel apart; a plain push below a pixel of blur), defaults 25% and 8; zoom scales exponentially about the centre (in: A from 1 to the factor with B from one over the factor to 1 fading in over it; out: the reverse), with an optional radial blur of up to `samples` taps over a log-scale range peaking half way, defaults 300%, 30% and 6; spin turns A by the angle and B from minus the angle to rest (clockwise or anticlockwise, default 180 degrees), each scaled just enough to cover the frame (|cos| + aspect |sin|) times a zoom swelling to the parameter half way, dissolving in the middle half; swirl twists both by the angle times (1 - r/R)^2 and sin(pi t) (R a fraction of half the shorter side, default 540 degrees and 100%, the inscribed circle) while dissolving in the middle half; roll turns A and B half a turn clockwise about the middle of the frame edge a quarter turn clockwise from the direction, B starting folded out of sight across that edge. All return exactly A at progress 0 and B at 1. The wipes' edge kernel and composite moved into the prelude with the moved-frame helpers.
- **Reason:** One mapping with one edge rule keeps every motion seamless (push and roll halves have complementary coverage) and honest about uncovered areas without stretching edge pixels. A transition is one pass (Decision 48), so a blur is a number of taps; at 4K each tap of a long blur costs about one read of a frame, so the defaults trade ghosting (8 whip taps with rows staggered into streaks; 6 zoom taps) against GPU time, and per-pixel staggering, which scatters the reads, cost two to three times as much.
- **Details:** `assets/transitions/{push,slide,whip-pan,zoom,spin,swirl,roll}/`, category `motion`; `crates/render/tests/motion.rs`; visual cases `push` to `roll`.
- **Consequences:** At 4K the blurred whip pan and zoom take about 5 to 7 ms of GPU time (median over the transition, shared machine), over the 3 ms aimed for and held only to the 8 ms frame budget; a downsampled multi-pass blur would need the transition framework to allow more than one pass. Zoom out minifies A without mipmaps (aliasing at strong factors), and roll leaves transparent corners on the way.

## 63. Keyframes: curves in source time, After Effects-style bezier handles, one solver copied with a cross-check

- **Date:** 2026-10-11
- **Decision:** Schema v7 adds `project::keyframe`. Every animatable numeric parameter holds either its constant or a `Curve`: clips carry `keyframes` by `ClipParam` (position, scale, rotation, anchor, crop left/top/right/bottom and feather, opacity, gain in dB, each with a `ParamDef` for its kind and range), effects carry `keyframes` by parameter id (float, int, point, angle and colour parameters whose schema marks them keyframeable; booleans, choices and text never animate). While a curve exists the stored constant is ignored and kept. Keys are in source time (seconds of the clip's media), sorted, unique and at or after zero, all of one value kind. Each key's interpolation describes the segment to the next key: `linear`, `hold`, or `bezier` holding this key's out handle and the next key's in handle, After Effects-style: a speed per value component (value units per second of source time) and an influence from 0 to 1 of the segment's duration. Evaluation is exact at keys, gives the first key's value before it and the last key's after it, and works per component: points per axis, colours per channel of their linear-light working-space RGBA (straight alpha), angles unwrapped (0 to 720 turns twice), ints rounded after interpolating; readers clamp to the parameter's range. Edits: turn a constant into a one-key curve at a time and back (keeping the value at a time; removing the only key does the same), add or replace, remove and move keys (moving past neighbours re-sorts; landing on another key is refused), set the interpolation, set one handle (in or out; it must belong to a bezier), scale selected keys' times about an anchor by a positive rational (exact; their handle speeds divide by the factor) and their values about an anchor by a finite factor (per component, clamped; speeds multiply). Influences are clamped to 0..1 on edit and refused outside it on load.
- **Reason:** Source time is how clip markers already behave, and it is the one base where trims, slips, moves and speed changes (either `SpeedKeep`) leave keys on the frames they were set on without rewriting any key; it also lets Phase 7 speed ramps map time through the speed map without touching curves. Speed and influence keep a handle valid whatever happens to the neighbouring keys (influence is a fraction, so time can never run backwards, the CSS cubic-bezier condition), make a smooth key just equal speeds on both sides, and are what velocity dialogs and a speed graph show; Premiere-style (time, value) offsets would need re-clamping on every key move. Keys addressed by their time rather than ids keep the file small and need no id allocation per key, since times are unique in a curve. `project` may not depend on `render` and `render` not on `project`, so the 30-line cubic-bezier solver is copied rather than moved into a new shared crate; a test in `engine`, which depends on both, compares them bit for bit.
- **Details:** `project::keyframe` (`Curve`, `Key`, `Interpolation`, `Handle`, `ClipParam`, `KeyTarget`, `HandleSide`, `cubic_bezier`, `EASE_INFLUENCE`), `Clip::{keyframes, curve, constant, param_at, transform_at, crop_at, opacity_at, gain_db_at, timeline_time_of}`, `Effect::{keyframes, curve, param_at}`, `Project::{param_value_at, param_curve, animate_param, make_param_constant, set_key, remove_key, move_key, set_key_interpolation, set_key_handle, scale_key_times, scale_key_values}`, `EditLabel::{Animate, StopAnimating, AddKeyframe, ChangeKeyframe, DeleteKeyframe, MoveKeyframe, KeyframeInterpolation, KeyframeHandles, StretchKeyframes, ScaleKeyframeValues}`, the `EditError` key variants, `project::schema::migrate_v6_to_v7`, autosave format 7; tests `crates/project/tests/keyframes.rs`, `crates/project/tests/schema.rs` (`v7-keyframes.json`), `crates/project/tests/autosave.rs`, `crates/engine/tests/keyframe_easing.rs`.
- **Consequences:** The engine and renderer must read clip properties and effect values through the `*_at` readers with `Clip::source_time_at`, not the constant fields. The inspector writes a key at the playhead (instead of the constant) while a parameter is animated. Transition parameters and adjustment items (no source time) are not animatable yet; an adjustment layer's effects will need item-relative key times. Keys on a clip whose speed map becomes a ramp keep working once `source_time_at` follows the ramp. Spatial (motion path) beziers, separate dimensions and loop behaviours before and after the keys would be new fields on `Curve` with a schema bump.

## 69. Nested sequences and compound clips: a clip source of media or a sequence, a compound flag, refused cycles

- **Date:** 2026-10-11
- **Decision:** Schema v8 gives every clip a `source` (`ClipSource::Media(MediaId)` or `ClipSource::Sequence(SequenceId)`), serialised flat in the clip as `"media": <id>` (the v7 shape) or `"sequence": <id>`, and every sequence a `compound` flag. A clip of a sequence (a nested clip) shows that sequence's timeline: its source time is the nested sequence's timeline time, so source start, speed, trims, slips, clip markers and keyframes keep their meaning, and its source length is the nested sequence's duration, the end of its last item on any track (`Project::sequence_duration`). The two sequences keep their own formats; when their frame rates differ, a parent frame shows the nested frame nearest its source time, halves to the later frame (`Sequence::nearest_frame`), and past the nested sequence's end a clip shows nothing (nothing is conformed, and edits do not refuse a nested clip longer than its sequence, as they do not for media). A nested clip on a video track contributes the sequence's picture, on an audio track its sound. A compound clip is a nested clip whose sequence is marked `compound`: hidden from the browser (`Project::browser_sequences`) and made by `nest_items` from a selection in one sequence that holds either sound (audio tracks only) or picture (video tracks, with subtitle and adjustment tracks beside them; at least one video track). The selected items move, keeping their ids and their places relative to the selection's start, into a new sequence with the parent's format and a track of the same kind and name for every parent track; transitions whose clips all moved go with them, transitions joining a moved clip to one left behind are removed (the edge cannot hold a transition across two sequences, and refusing would block the common case of a dissolve into the selection); one clip from source time 0 at speed 1 covers the selection's span on the topmost selected video (or audio) track. `break_apart` is the inverse for any nested clip at speed 1: the n-th track of each kind goes to the n-th track of that kind in the parent, items are trimmed to what the clip shows, transitions come along when all their clips do, and the clip's own properties are dropped; a compound nested by no other clip moves out with its ids and is removed (so nesting then breaking apart gives back the same tree, with a higher id counter), anything else is copied with new ids. `set_clip_source` points any clip at media or a sequence, `insert_sequence_clip` places a sequence as a clip, `duplicate_compound` gives a clip its own deep copy of a shared compound (new ids throughout, compounds inside copied, other nested sequences shared), and `remove_sequence` deletes a sequence, refused while a clip nests it (`SequenceInUse`). A sequence never contains itself, directly or through others: edits refuse it with `NestingCycle { parent, child }` and `Project::validate` refuses such a file. A compound whose last clip is deleted stays in the project, hidden, so the clip can come back by paste; no edit prunes it. `Project::check_transition_media` measures a nested outgoing clip's tail handle against the nested sequence's length without asking the caller, `HandleNeeds` reports `ClipSource`s, relinking and `source_used_until` see media clips only (clips inside compounds included), and `clip_count` counts a media's clips through every clip that nests a sequence, starting from the browser's sequences. `engine::timeline::TimelinePlan` leaves nested clips out and counts them (`nested_clips`): they show nothing until the renderer composites a nested sequence as a layer. Frame rates are stored in lowest terms by `add_sequence_with`, `set_sequence_format` and `set_project_settings`, so `50/2` for a `25/1` sequence is a no-op; loaded files may hold any form. New undo labels: New Compound Clip, Break Apart Clip, Replace Clip Source, Make Compound Clip Independent, Delete Sequence. Autosave format 8 began with schema v8; `migrate_v7_to_v8` adds `"compound": false` to every sequence.
- **Reason:** One source type keeps every clip edit, keyframe rule and handle check working unchanged for nested clips, and the flat file form leaves v7 clips as they were. A full format per sequence (Decision 55) already makes nested formats independent; mapping by source time and taking the nearest frame is how a 24 fps title sequence plays in a 25 fps edit without retiming either. Track kinds already split picture from sound (a media clip with both appears as a video clip and an audio clip), so a compound of one kind fits the model; mixed audio and video selections would need two linked clips, which the linking task (Phase 6) brings. Keeping ids when a compound moves in and out makes nesting reversible and keeps autosave diffs small; copying with new ids keeps ids unique when the content stays elsewhere. Refusing cycles and deletions of nested sequences is safer than cascading.
- **Details:** `project::nest` (`Project::{browser_sequences, sequence_duration, sequence_users, contains_sequence, insert_sequence_clip, set_clip_source, nest_items, break_apart, duplicate_compound, remove_sequence}`, `Sequence::{nearest_frame, nested}`), `project::model::{ClipSource, Clip::source, Sequence::compound}`, `EditError::{NestingCycle, SequenceInUse, NothingToNest, NestAcrossSequences, NestMixedKinds, NestNeedsClipTrack, NotNested, NotACompound, BreakApartSpeed, BreakApartNoTrack}`, `EditLabel::{Nest, BreakApart, ReplaceSource, DuplicateCompound, RemoveSequence}`, `SequenceFormat::reduced`, `project::schema::migrate_v7_to_v8`, `engine::timeline::TimelinePlan::nested_clips`; tests `crates/project/tests/nested.rs`, `crates/project/tests/schema.rs` (`v8-nested.json`), `crates/project/tests/settings.rs`, `crates/engine/tests/nested_plan.rs`.
- **Consequences:** The renderer must composite a nested sequence as a layer (plan the child's segments in its own time, map each parent frame to the nearest child frame, then apply the nested clip's look) before nested clips show; until then they draw nothing. Open-in-place (editing a compound's timeline inside the parent's) is UI. Copy and paste must carry a compound with its clip across projects and may decide whether to prune compounds no clip nests. Linked audio and video (Phase 6) can lift the one-kind rule by placing a linked pair of nested clips.

## 65. Subtitle export: sidecars from the model, `mov_text` and WebVTT streams, burn-in from the frame size

- **Date:** 2026-10-11
- **Decision:** Sidecar SubRip and WebVTT files are written by `project::subtitle_export` (`track_cues`, `to_srt`, `to_vtt`): cues in whole milliseconds relative to the export range, exact times rounded to the nearest millisecond with halves away from zero, cues crossing the range edges cut at them, a cue that rounds to nothing or has no text left out, blank lines inside a cue dropped, `\n` line ends, UTF-8 without a BOM; SubRip numbers cues from 1 and carries the text as it is, WebVTT escapes `&`, `<` and `>` and writes no cue settings (the model has no position or style until Phase 10). Embedded subtitles go through `media::export::ExportSession`: `ExportSettings::subtitles` (`SubtitleSettings { language, title }`, the language an ISO 639-2 code) and `push_subtitle(stream, &SubtitleCue)`, encoded by FFmpeg's `mov_text` (MP4, MOV) and `webvtt` (Matroska, WebM) encoders, one packet per cue timed in milliseconds; other containers refuse subtitle streams. Burn-in is `render::subtitle`: `cue_at`, `SubtitleStyle::lay_out` (font size 5% of the frame height, lines wrapped at the title-safe width and centred, the last line's bottom on the safe area's bottom edge, a 5% margin per side, white fill, black outline 8% of the font size, 60% black shadow offset 5% and blurred 8% of the font size) and `add_burn_in` (the text composited over the frame). Wiring the three into the export pipeline waits for the export queue.
- **Reason:** `project` depends on no other crate, and the sidecar text needs only the model, so the writers live there and the engine converts project cues to `media::SubtitleCue` for embedding and burn-in. Rounding is monotonic, so items that do not overlap in exact time do not overlap in milliseconds, and the only cue that could end at its start is one shorter than a millisecond. `mov_text` (3GPP timed text) is the text track QuickTime and MP4 players show; WebVTT is the only subtitle codec WebM allows and Matroska carries it too, so one text codec per container family covers every container with subtitles. Sizing the burn-in from the frame keeps it the same proportion at every export size; 5% of the height is about 54 px at 1080p, inside the usual broadcast range, and EBU R 95 puts 16:9 title-safe at 5% per side.
- **Details:** FFmpeg's text encoders read ASS dialogue lines, where `\N` breaks a line, `{\` opens an override block and a backslash before `n`, `N` or `h` is an escape: the session writes line breaks as `\N` and follows each backslash, and the `{` of a `{\` pair, with a word joiner (U+2060), as FFmpeg's own decoders do; `read_subtitle_cues` removes them when reading back. The `webvtt` encoder writes text as it is, so the session escapes `&`, `<` and `>` first. MP4's empty samples between cues are written by FFmpeg's muxer. Tests: golden `tests/fixtures/subtitles/sample.srt` and `sample.vtt` (29.97 fps times, two lines, markup characters, CRLF and blank lines, past an hour), rounding and range cuts in `project`; `crates/media/tests/subtitles.rs` writes MP4 (VideoToolbox trial and x264), MOV and Matroska with two streams and decodes every cue back (start, end, text, language, title); `crates/render/tests/subtitle.rs` (cue at a time, size, centring, wrapping, the cue over a frame on the GPU) and the visual case `subtitle_burn_in`.
- **Consequences:** WebM subtitles are accepted but untested here, since WebM needs AV1 or VP9 video and the pinned FFmpeg build has neither encoder (Decision 47). A cue's text containing `{}` loses the braces in a reader that treats them as an empty override block. Styled cues (italics, colour, position) come with Phase 10's caption styles: `mov_text` style boxes and WebVTT tags and cue settings then come from the model.

## 75. Animated and nested rendering: looks per frame at the source time, nested sequences as layers with flattened decode segments, per-frame cache keys from what a frame shows

- **Date:** 2026-10-11
- **Decision:** `engine::timeline::TimelinePlan` keeps an `Animation` (the clip and its item start) for every clip with a curve on something it draws (a transform field, crop, opacity, or a parameter of an enabled effect with a renderer; gain alone does not count) and evaluates its look per timeline frame at the source time the frame shows (`TimelinePlan::look_at`, through `Clip::{transform_at, crop_at, opacity_at}` and `Effect::param_at`, so LUT intensity animates); clips without curves keep the one constant look. Transition parameters stay constant. A clip of a sequence is a `NestedLook`: the nested sequence's own plan (built once per build, recursion stopped at `MAX_NESTING_DEPTH` = 16 with deeper clips counted in `nested_clips`), the clip's look, and its time mapping: parent frame to nested time through the clip's source start and speed, then the nested frame nearest it (halves later, `Sequence::nearest_frame`), nothing before the nested start or at and past its length. The nested plan's decode segments are flattened into the parent's `segments()` over the parent frames whose nested frame they cover, their source time mapped through both clips and their speed the product of both, so nested media joins the parent's look-ahead, scrubber, `FrameDesc::segments` and the export's decode path unchanged; when the parent frames fall between nested frames (another rate, an off-grid source start or a speed that does not step whole nested frames) each nested frame is sampled half a nested frame late, which picks the nested frame's own media frame for media no finer than the nested rate. `TrackFrame::Nested { nested, frame }` and a transition's `outgoing_nested`/`incoming_nested` render the nested frame recursively in the same graph: when the nested canvas equals the level's and the clip places it as it is (identity transform, no crop, opaque, normal blend, no effects) its layers go straight into the parent stack if they all blend normally, which composites exactly what the same clips placed flat do; otherwise the nested composite renders at its canvas times the level's scale and is placed like a clip whose picture is the nested canvas (crop scaled to its texels), through the clip's effects. `span_hash` keeps one hash per run of frames with constant looks; a run that shows an animated look or a nested clip carries a flag, and each of its frames adds the evaluated look (hashed with what the clip shows of its source) and, for a nested clip, the nested frame, the nested plan's own `span_hash` of it and the clip's evaluated look.
- **Reason:** Evaluating at the source time is how keys are stored (Decision 63), so trims, moves and speed changes keep every animated frame's key. Keys from evaluated values (not from the curve) mean a key edit misses exactly the frames whose values changed, frames before the first key and after the last share values with their neighbours only through the frame index, and an edit elsewhere misses nothing. Flattening keeps one look-ahead, one decode path and one cache index for any nesting, at the cost of linear segments: a per-frame mapping would need a segment per parent frame (a seek each) or a look-ahead change; the half-frame offset is exact for the common case (media at the compound's rate) and only differs, by less than a nested frame, for media finer than the nested rate. Inlining the plain case makes a compound clip bit-identical to its clips placed flat; a group pass elsewhere gives the nested composite its own isolation (opacity and blend modes act on the whole picture) as editors do.
- **Details:** `crates/engine/src/timeline/{animate,nested,plan,render}.rs`; `TimelinePlan::{look_at, is_animated, nested, nested_looks}`, `NestedLook::{plan, frame_at, segment, look_at, is_animated}`, `MAX_NESTING_DEPTH` (all additive); `TrackFrame::Nested` and `TransitionLook::{outgoing_nested, incoming_nested}` are new variants and fields (no code outside `engine::timeline` matched or built them). `crates/engine/tests/timeline_layers.rs` (GPU and media), `crates/engine/tests/nested_plan.rs`, unit tests in `nested.rs`. The reference project's picture in picture fades in by keys and sits in a compound clip.
- **Consequences:** The look-ahead's overlap limit (`decode_workers` segments at a frame) now counts a nested sequence's tracks too. Nested audio is the mixer's (it skips nested clips until it plays them). Motion blur (Phase 13) can sample `Animation` at sub-frame source times. A look-ahead with per-segment time maps would make nested media finer than the nested rate exact.
## 73. Audio mixer: one graph for the callback and export, control-point gain ramps, graphs swapped through a ring

- **Date:** 2026-10-11
- **Decision:** The mixer is `audio::mixer::Graph`, built off the audio thread from a `GraphSpec` with every buffer it uses. Track strips take one feed each (clips already decoded, resampled to the mix rate, mixed to the layout and scaled by clip gain) and apply fader (dB, -96 and below is silence, +12 at most), pan and mute/solo (audible when not muted and, if any track is soloed, soloed itself; mute wins; a silent strip's sends are silent), then add into the master or a bus; sends add the feed (pre-fader: before fader and pan) or the strip's output (post-fader) at their level. User buses are strips that run after the tracks in index order and may only feed buses with a higher index, so routing cannot loop. The master applies its fader and a clip guard that never limits: overs above full scale and the highest sample are reported (`MeterBank::clip`), and an optional soft clip (off by default) bends everything above -1 dBFS towards full scale with a tanh. Pan is constant power normalised to unity at the centre (`√2 cos θ`, `√2 sin θ`, θ = (pan + 1)π/4): a strip at its defaults passes its feed unchanged, and on the stereo feeds (every feed is in the mix layout) pan is a balance; mono ignores pan, 5.1 pans the front and surround pairs alike and leaves centre and LFE. Every gain is evaluated at control points every 32 timeline frames (absolute multiples) from the settings and the fader, pan and master automation lanes, and ramps linearly per sample in between; a command (fader move, mute) ramps to its new value by the next control point. Meters (peak, RMS, peak hold of 1.5 s, per channel, for every strip, bus and the master after the guard) publish into atomics every 800 frames at 48 kHz (the nearest whole number of control segments to a sixtieth of a second), each graph with its own `MeterBank`. `audio::mixer::Mixer` runs the graph inside the callback (`OutputStream::open_with_mixer`, `OfflineOutput::with_mixer`): a graph arrives with the consumer of its own feed ring (`Feed`, one interleaved frame of every track's channels per timeline frame, from a start frame) through an `rtrb` command ring, alongside play, pause and setting changes; `SwapAt::Now` (start, seek) makes it live at the next callback, `SwapAt::Continue` (an edit) when the live graph reaches the new feed's start, splitting a callback there; retired graphs go back through a return ring and are dropped by `MixerControl::collect`. A feed that runs dry while playing is mixed as silence, counted as an underrun, and the playhead moves on (late frames are dropped), so audio stays on the clock. `engine::mix` builds graphs from a sequence's audio tracks (top to bottom, strip id = track id) and `MixSettings` (per-track fader, pan, mute, solo, output, sends and fader and pan automation as project `Curve`s in sequence time, buses, master); `lane_from_curve` maps linear and hold keys one to one and flattens bezier segments through `Curve::value_at` every 5 ms. The clip side (`glass-audio-decode` for playback, the caller's thread offline) opens one `media::AudioReader` per clip a second before it plays, at the mix rate divided by the clip's constant speed (so speed changes pitch, like tape; speed ramps and nested sequence clips are silent and counted), and applies clip gain from `Clip::gain_db_at` at the same control points. `AudioPlayback` keeps the feed ring 8192 frames (170 ms at 48 kHz) ahead, also while paused, builds a new graph and feed on a seek (now) or an update of the project or settings (continue, after what is queued), and forwards setting changes as commands. `OfflineMix` and `mix_range`/`mix_range_with` render the same graph block by block for export.
- **Reason:** The callback may not allocate, lock or wait (Decision 33), so everything it touches is preallocated and arrives through `rtrb` rings (Decision 27, 34), and nothing is freed on it. Evaluating gains on an absolute 32-frame grid makes the output a function of the timeline alone, so export, playback and any device buffer size give the same samples (tests compare them), while costing a few hundred gain evaluations a second per strip; a 32-frame ramp is short enough for sample-accurate automation (the chord error of a dB ramp over 32 frames is under 1e-6) and long enough to keep moves free of clicks. Unity-at-centre pan keeps the default mix equal to the clips' sum, which the export and the tests rely on, and stays constant power across the range. The project has no place for track mixer state and two schema bumps (v7, v8) were in flight, so mixer settings are an input, as track header mute and solo already are (Decision 68). A one-feed-ring-per-graph design keeps the feeder and the callback in step by construction: an edit's audio is heard after what was already queued (up to the ring's 170 ms) instead of needing a shared ring to be rewritten in place.
- **Details:** `crates/audio/src/mixer/` (`mod.rs` specs, laws, `graph.rs`, `automation.rs`, `meter.rs`, `realtime.rs`), `crates/audio/src/callback.rs` (mixer source), `crates/engine/src/mix/` (`mod.rs` settings and specs, `source.rs` clips, `offline.rs`, `playback.rs`), `crates/engine/src/export/run.rs` (`MixedAudio`); tests `crates/audio/tests/mixer.rs`, `mixer_alloc.rs`, `crates/engine/tests/mix_offline.rs`, `mix_realtime.rs`, `mix_export.rs`; `smoke` mixes 2 s of the reference project and checks the A1 tone's level, and its export pushes the mix instead of silence.
- **Consequences:** Track mixer settings, buses and automation are lost with the session until a schema version stores them on tracks and the sequence (and the UI's `TrackHeaderState` mute and solo should then feed `MixSettings`). Edits are heard about 170 ms late during playback. Audio transitions are not crossfaded, nested sequence clips and speed ramps are silent, and effects are not in the graph yet (Phase 12's effects line adds per-strip inserts). The export queue (`engine::export`) pushes the mix with every track at its defaults (a job carries no mixer settings yet) and checks loudness only when an audio clip plays in the range; an export without video may run to the end of the last audio item; the app does not open an `OutputStream` with the mixer yet, and `TimelinePlayback` still runs on a system clock.
## 70. Background export queue: one job at a time, a render thread beside the encoder, a temporary file renamed on success

- **Date:** 2026-10-11
- **Decision:** `engine::export::ExportQueue` runs `ExportJob`s one at a time in submission order on `glass-export`, which starts with the first job and exits when the queue is empty. A job holds an immutable project root (edits made meanwhile do not reach it), the sequence, the `ExportSettings` (usually a resolved preset, kept for verification's loudness target and limits), a range of timeline frames (the whole sequence by default) and the output path, and says what happens to one subtitle track: nothing, a SubRip or WebVTT sidecar next to the output, an embedded stream, or burned in. Per job the look-ahead decodes the range and a new `glass-export-render` thread (`Role::ExportRender`) renders every output frame with `TimelineRenderer::render_output`: full quality, never the adaptive governor, never the frame cache; the settings' size with the canvas fitted inside and centred; the output node encodes for the settings' colour tags (BT.709 with the inverse BT.1886 EOTF, PQ, HLG, sRGB) into `Rgba8Unorm`, `Rgb10a2Unorm` or `Rgba16Unorm` by the encoder's bit depth, from a working space chosen by the project colour space; a burned-in cue is composited over the frame in linear light before the output node. Frames are copied into a lossless four-buffer `ReadbackRing`; only when every buffer is taken does the thread wait, and then for the oldest frame's submission only. Finished frames reach `glass-export` through a two-frame bounded channel and their buffers come back for reuse; `glass-export` pushes the picture, silence up to the frame's end, and the embedded cues, then finishes the session, verifies the file, writes the sidecar and renames everything into place. An output frame rate other than the timeline's shows the timeline frame at each output frame's start. Pause blocks both threads at the next frame boundary with the session open; cancel stops both, drops the session and deletes the temporary files. The session writes `.<name>.<pid>-<job>.part` next to the output (an image sequence a hidden folder of frames), verified before it is renamed (sidecar first, then the output, so a failed rename removes the sidecar again); a file already at the output path is replaced only by a finished export. Events: `Queued`, `Started`, `Progress` (stage, frames done of total, fps and ETA over running time without pauses, at most every 100 ms, at each stage change and after the last frame), `Paused`, `Resumed`, `Finished` (files, encoder and fallbacks, `VerifyReport`, offline clip count), `Cancelled`, `Failed` (an `export.error.*` key with arguments). Finished and failed jobs carry a `Notification` (title and body i18n keys, the file name and finding count) that the app may show as an OS notification; the engine makes no OS calls.
- **Reason:** Parallel jobs would share the GPU, the one hardware encoder and the cores x264 and x265 already fill, and finish no sooner overall, so one at a time, in the order the user queued them, is simpler and as fast. Rendering on its own thread lets graph building and texture uploads overlap the colour conversion and encoding on `glass-export`, and waiting on the oldest submission rather than draining the GPU queue keeps several frames rendering ahead. A temporary file in the output's folder is on the same file system, so the rename is atomic and the final path only ever holds a complete, verified file. The file's tags must describe its values, so the settings' tags choose the output encoding, while the project colour space chooses the working space (Decisions 15 and 55); `export::colour_tags` gives the tags that deliver the project's own space for settings that follow the project. The engine has no sequence audio mix yet, so audio streams carry silence of the exact length and their loudness target is not checked; a silent stream would only report `export.verify.loudness.silent`.
- **Details:** `crates/engine/src/export/` (`ExportQueue`, `ExportQueueConfig`, `ExportJob`, `SubtitleExport`, `SidecarFormat`, events and `MESSAGE_KEYS`), `TimelineRenderer::render_output` and `FrameOutput` in `crates/engine/src/timeline/render.rs`, `Role::ExportRender`; i18n keys `export.stage.*`, `export.error.*`, `export.notify.*`; tests `crates/engine/tests/export_queue.rs`.
- **Consequences:** The in and out range, smart export and stills (next Phase 8 lines) extend the job's range and the render thread. The sequence audio mix (Phase 12) replaces the silence and brings the loudness check back. An HDR project exported with an SDR preset is gamut-converted and clipped until tone mapping exists. The app drains the event receiver once per frame and turns notifications into OS notifications; a second export queue (another window) would run its jobs alongside the first.
## 71. Multi-pass transitions: extra entry points drawn into targets at declared scales; whip pan and zoom blurred at a reduced resolution

- **Date:** 2026-10-11
- **Decision:** Amends Decisions 48 and 62. A transition's manifest may list up to 8 `passes` drawn in order before `fs`: each names a fragment entry point of its own `shader.wgsl` (several passes may share one) and its target's size as a fraction from 1/16 to 1 of the output's, one number or `{"along", "across"}` the direction of travel (along is y for up and down, x otherwise), with an optional floor `min` in pixels (never above the output's extent). `TransitionNode` declares the targets as extra outputs (aliased by the graph like any intermediate), draws the passes then `fs`, and binds A, B and the earlier targets as `pass0` to `pass7` (bindings 4 to 11; the current and later ones are the renderer's 1x1 placeholder, so every transition, single-pass ones included, has one bind group layout). The uniform's padding word is now `pass_index` (the pass drawn, the pass count in `fs`) and `pass_size` (that target's size) follows `size`, so the parameter slots start at byte 48. The prelude adds `sample_pass(i, uv)`, `size_of_pass(i)` and `sum_taps(texture, uv, step, n)`; `sample_pass` is a switch the GPU compiler may flatten into a read of every target, so hot loops take the target as a `texture_2d<f32>` parameter. The node's timestamps span all its passes. `shaders::validate_external` and `ShaderLibrary::add_external` take the entry points a source must define, so discovery reports a pass without its entry point and a hot-reloaded edit that drops one is rejected like a broken one. Whip pan: up to `samples` pixels of blur `fs` takes one tap a pixel (an exact box); beyond, `strip` lays A and B edge to edge along the direction over a quarter of the output's extent (two frames, so 8 output pixels a texel at any size above 256 texels; full resolution across), each texel the box over its cell and only where `fs` can reach, then three `smear` passes of up to `samples` taps at spacings growing by that factor make one evenly spaced comb of up to samples^3 taps as long as the blur, read filtered by `fs`, which mixes it in between `samples` and twice that. Zoom: the shrinking frame (A out, B in) gets a pyramid of four halvings (`reduce`), read between the two levels around its footprint (one pair per pass, chosen before the per-pixel work); the radial blur takes one tap a pixel in `fs` up to `samples` pixels and beyond is drawn from `small` (the unblurred zoom at a quarter resolution, at least 256 texels, over a margin of e^(spread/2) about the centre, the blur's outward reach) smeared by three passes in log scale with the same comb, mixed in up to twice `samples`; the blur now applies to the composed picture rather than to each frame before composing. `samples` now bounds the taps per pixel of each pass; defaults unchanged (8 and 6).
- **Reason:** At 4K a sparse tap costs about a full read of a frame, so one pass with 6 or 8 taps cost 5.3 ms (whip pan) and 2.6 ms (zoom) half way back to back on the M5 (shared with other agents), and its few taps showed as ghost copies (rows staggered into streaks for the whip pan). The reduced passes read A and B about once, the combs read small textures with good locality, and a comb of combs at multiplied spacings is one evenly spaced comb, so three passes of n taps give n^3 with no gaps at default settings: 1.50 ms and 1.57 ms half way back to back, and in `motion_transitions_at_4k_gpu_time` medians over the transition of 1.44 ms and 1.68 ms against 6.35 ms and 6.14 ms before. Entry points in one file keep discovery, embedding and hot reload as they were; a fixed vocabulary of operations would have needed Rust for every new kind of blur. Full resolution across the whip's direction keeps detail the motion does not smear; the floor keeps small renders (thumbnails, previews, tests, the 320 x 180 visual goldens) near full resolution, where nothing is saved; the dense taps below `samples` keep short blurs exact.
- **Details:** `crates/render/src/transition/{mod.rs,node.rs}` (`Pass`, `Transition::passes`, `entries`), `crates/render/shaders/transition.wgsl`, `crates/render/src/shaders.rs`, `assets/transitions/{whip-pan,zoom}/`, `assets/transitions/README.md`; tests `crates/render/tests/transition.rs` (passes discovered and drawn in order at their sizes, broken passes reported, a pass's entry point hot reloaded and kept when an edit drops it), `crates/render/tests/motion.rs` (zooming out to about 1/7.5 a one-pixel checker is within rms 0.02 of its box-filtered 0.5, against 0.125 before; the 4K timing through `common::timing` with every transition, whip pan and zoom included, held to 3 ms; its GPU tests hold the timing lock). Visual goldens `whip_pan`, `zoom` and `zoom_out` regenerated: the whip pan's streaked rows and the zoom's stepped copies at the edges are now smooth blurs, slightly softer at the start of the blur.
- **Consequences:** With the GPU idling between frames (16 ms gaps) both blurred transitions still take 5.4 to 5.9 ms, as the old single passes did (5.8 to 6.9 ms): at a low GPU clock, five or nine dependent passes cost about what the sparse taps did, so a real-time player that leaves the GPU idle between frames sees little of the gain until the GPU is kept busy. Memory at 4K: whip pan's four targets 66 MB, zoom's eight 39 MB. The reduced path adds about two of its texels of softness (16 px along the whip at 4K) where the blur hands over from the dense taps. A shrinking zoom beyond 16x (up to the 20x maximum) still undersamples at the last level. The motion transitions other than whip pan and zoom are unchanged.
## 74. Canonical project file: pretty JSON, declared field order, sorted maps, exact floats, no schema bump

- **Date:** 2026-10-11
- **Decision:** `project::schema::save` writes one canonical form: pretty JSON with a 2-space indent, one key or array element per line, `\n` line ends and one trailing newline; the envelope and every node as structs with fields in declaration order (Decision 45 and the model's source give the orders); every JSON object that is a map with its keys in ascending byte order, which for clip `keyframes` means by property id (`crop.left`, `opacity`, `position`, ...) through `keyframe::serialize_clip_curves` instead of `ClipParam`'s declaration order (effect `keyframes` and `params` were already sorted by id); lists in model order; ids as numbers, times as reduced fractions; floats in their shortest form that parses back to the same bits, with `serde_json`'s `float_roundtrip` feature enabled in `project` so the parse is exact (the default parser is best effort and can be one ulp off); no timestamps, no machine data beyond the media paths the user chose, and nothing hash-ordered. `load` reads any layout and key order; saving such a file writes the canonical bytes. The schema version stays 8: the change is formatting only and every v8 file, in the old or new clip keyframe order, loads the same. The v8 fixture with animated clip properties (`v8-keyframes.json`) was regenerated; older fixtures stay as written.
- **Reason:** Project files are meant to live in git, so one edit should be one small diff, and the Phase 5 Done when needs a 1000-clip project to save, load and save byte-identically. One sorting rule for every map is easier to state and to check than per-map orders. A schema bump would add a migration that does nothing.
- **Details:** `project::schema` module docs, `project::keyframe::serialize_clip_curves`, `crates/project/Cargo.toml` (`float_roundtrip`); tests `crates/project/tests/canonical_json.rs` (1000 clips over three sequences plus a compound: save, load, save identical; sorted-compact, reversed-compact and 4-space CRLF files save to the canonical bytes; key order golden `tests/fixtures/canonical/key-order.proj`, rewritten with `GLASS_UPDATE_FIXTURES=1`; random edits save the same bytes in a second process with other hasher keys; 200,000 random f64 and f32 values round-trip bit for bit).
- **Consequences:** Every later model change keeps maps sorted and avoids hash-ordered collections in serialised types; the golden test fails on any change to the bytes of an unchanged tree. Autosave (Decision 22) serialises the same model types, so its clip keyframe maps are sorted too, which its readers ignore.
## 72. The timeline view: a float position in frames, exact times out, zoom from a frame to the whole sequence, rulers on timecode values

- **Date:** 2026-10-11
- **Decision:** `ui::panels::timeline::view::TimelineView` is UI state per open sequence (not in the project file): the left edge as a frame position and the zoom as points per frame, both `f64`, plus the tracks' vertical scroll. Conversions out are exact: `x_to_time` is the `Time` of the nearest frame boundary, `frame_at_x` the frame under a point, `time_to_x` measures from the exact frame count. Time runs left to right in every locale; only the header column mirrors. Zoom runs from 96 points per frame down to the whole sequence (at least 10 seconds) with 24-point margins, which is also zoom to fit; the left edge goes from a margin before zero to where the end sits mid-view, on whole-frame bounds. Zoom to fit, zoom to a caller's range (centred when the range is too short for the closest zoom) and minimap drags put the left edge on a frame boundary; pinch, scroll and keyboard zoom keep the time under their anchor fixed instead. Input reads egui's raw events: a pinch, or a wheel with Ctrl, ⌘ or Alt held, zooms about the pointer by `exp(points / 200)`; a wheel pans (a trackpad on both axes, a mouse wheel through the tracks) and Shift makes it horizontal. `view.zoom_in` and `view.zoom_out` step by 2x about the playhead when it is on screen, else about the middle, and repeated presses build on the running animation's end; they and zoom to fit or to a range animate for 150 ms (ease-out cubic, zoom moving evenly in log scale about the screen point both ends agree on) unless `reduced_motion` is set, and any gesture stops an animation where it is. The ruler places ticks on timecode values (steps: the divisors of a second in frames, then 1, 2, 5, 10, 15, 30 seconds and minutes, then hours; labels at least the widest label plus 16 points apart, minor ticks at least 6 points apart and at most ten per label), formats `HH:MM:SS:FF` with `;` before the frames in drop-frame, and puts a minute tick that drop-frame skips on the minute's first frame (`00:01:00;02`). Edit snapping gets a hook only: `SnapTargets` (times with a `SnapKind`, kept sorted) and `TimelineView::snap`, which snaps within 8 points on screen and otherwise to the nearest frame.
- **Reason:** Continuous gestures need a continuous position, while every edit must land on the frame grid in exact `project::Time`, so the float stays inside the view and only frame-exact times leave it. Reading raw wheel events is needed because egui turns Alt-scroll into vertical scrolling and Cmd-scroll into its own zoom delta. Ticks on timecode values keep labels round in drop-frame and at 23.976 and 29.97 non-drop, where real seconds and timecode seconds differ. No zoom-to-selection command was added: every command needs a Glass key from `Sheet / Keyboard`, which has none for it, and a new command changes the shortcuts editor's goldens; the selection and zoom tool tasks call `zoom_to_range` and can register the command with a key from the board.
- **Details:** `crates/ui/src/panels/timeline/{view,ruler,minimap}.rs`; tests `crates/ui/tests/timeline_view.rs`; snapshot cases `timeline_ruler_*`, `timeline_minimap*`, `timeline_view`. The Paper board (03 Timeline) could not be read (the design server timed out on every try), so sizes come from the tokens: ruler 28 points (`row/pro`), minimap 24 (`control/pro`), monospace caption labels in `text/secondary`, ticks in `border/strong`, the minimap window `accent/soft` with a `border/strong` edge (`accent` on hover), lanes on `bg/0`.
- **Consequences:** The ruler, minimap and zoom slider need a pass against the 03 Timeline board once it can be read. The ui crate has no system reduce-motion setting yet; the app sets `reduced_motion` when it has one. Later timeline tasks (clips, playhead, markers, selection, tools) draw and hit-test only through the view's conversions.

## 78. Clip rendering: a UI-thread analysis store fed by the job pool, tiles anchored on the clip, levels picked per zoom, blocks when zoomed out

- **Date:** 2026-10-11
- **Decision:** `ui::panels::timeline::clips::clips` draws the items of a sequence over the lanes, culled per track by a binary search on the visible range. Analysis results reach it only through `ui::panels::timeline::clip_media::ClipMedia`, a UI-thread store of thumbnail strips, atlas textures (keyed by level index and chunk, so lookups allocate nothing) and peaks per `MediaId`. A miss draws a placeholder and queues one `MediaRequest` (deduplicated until `forget`); `AnalysisFeed::pump`, called once a frame, submits thumbnail and peak requests as `ThumbnailJob` and `PeaksJob` at `Priority::Visible`, polls the handles with `try_result` and stores the results, and returns the atlas loads for the caller to decode off the UI thread with `ThumbnailStrips::load_atlas` before `ClipMedia::insert_atlas` uploads them. Thumbnail tiles are laid from the clip's start, one per thumbnail width (the strip's aspect at the body's height), each showing the source time at its left edge, `source_start + offset × speed`; the strip level is the coarsest whose interval is at most one tile's source span, else the finest loaded, and only visible tiles are looked up. Waveforms draw one column per point from `Peaks::level_for(sample_rate × speed / points per second)`, scaled by the clip gain (its curve when keyframed) and clipped at full scale, one lane for mono and two (the first two channels) for stereo and wider. The name bar shows the nested sequence's name or the media file's name (the model has no clip name), kept on the visible part of the clip and cut with an ellipsis, with badges on its far side (the bar mirrors in right-to-left locales): `fx`/`fx N` for a non-empty effect stack, the speed as a percentage or `Ramp`, a stacked-frames mark for nested and compound clips, a diamond when the clip or an effect is keyframed; badges drop before the name gets under 24 points. Disabled clips are dimmed by an overlay to the `opacity.disabled` token; a missing media reference draws in `clip/offline`. Transitions are glass blocks (`bg/3` at the `glass` opacity, `glass/edge` outline, a diagonal) over their span below the name bar, with the cut line drawn through them, so the alignment reads from where the block sits. Clips narrower than 12 points, and every clip below 0.5 points per second, are plain blocks, and touching blocks of one colour merge. All shapes are collected per layer (bodies, one mesh per atlas texture, one waveform mesh, fronts, transitions) and painted once. Selection and colour labels come through the `ClipHooks` trait (`&()` for none).
- **Reason:** The UI thread must never block, and a store of what is already loaded with a request queue keeps the renderer pure and testable without a pool; the pool already deduplicates and caches jobs on disk. Atlas decoding is file I/O, and the ui crate has no worker thread of its own, so it stays with the caller (the app shell owns the threads). Tiles anchored on the clip do not swim while scrolling, and picking the coarsest sufficient level loads the fewest atlases while every tile still differs. One column per point keeps waveform cost proportional to the visible width.
- **Details:** `crates/ui/src/panels/timeline/{clips,clip_media}.rs`; tests `crates/ui/tests/timeline_clips.rs`; snapshot cases `timeline_clips_*` (thumbnails and peaks made up from theme colours and a deterministic signal). The Paper board (03 Timeline) could not be read (the design server timed out on three tries), so the look comes from the tokens: `radius/control` corners, a 16-point name bar in the clip colour with `text/inverse` caption text, the body at 30% of the clip colour, `border/subtle` edges and the 1.5-point `accent` selection outline.
- **Consequences:** No window wires `AnalysisFeed` and an atlas loader yet (the app shell does when it exists). Nested sequences show no thumbnails until the engine can render them into a strip. Clips need a pass against the 03 Timeline board once it can be read.
